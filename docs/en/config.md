# Configuration: the agsy.yaml Reference

`agsy.yaml` is agsy's only configuration file. It lives at the project root and **should be version-controlled** (the output directory `.agsy/` should not).
It is normally generated by the `agsy init` questionnaire; this chapter explains every field so you can edit it by hand with confidence.

## Complete example

```yaml
# agsy config file (agent-sync)
# Path syntax: ~ prefix = home expansion; relative = resolved from this file's directory; absolute = as is
version: 2

sources:                      # ordered array, earlier entries win
  - ~/all-ai-lib
  - ./repo-ai-lib

build:
  out: .agsy                  # must be inside the project (apply wipes it entirely)

  categories:                 # source subdir → output subdir (from / to values must each differ)
    rules:     { from: rules, to: rules }
    skills:    { from: skills, to: skills }
    workflows: { from: workflows, to: workflows }
    hooks:     { from: hooks, to: hooks }

  on_conflict:                # same-name handling: first / rename / error (required per category)
    rules:     rename
    skills:    error
    workflows: rename
    hooks:     error

  tools: [claude, codex, antigravity, cursor]   # valid values for a workflow's target: front matter

mount:
  - dir: .                    # project root: AGENTS.md for Codex / Cursor / Antigravity
    links:
      AGENTS.md: AGENTS.md
  - dir: .claude              # Claude Code
    links:
      rules:  rules
      skills: skills
    merge:                    # hooks merged into settings.json's "hooks" key (other keys untouched)
      settings.json: hooks.claude.json
  - dir: .agents              # Codex + Antigravity + Cursor
    links:
      skills:     skills
      workflows:  workflows
      hooks.json: hooks.antigravity.json
  - dir: .codex               # Codex hooks
    links:
      hooks.json: hooks.codex.json
  - dir: .cursor              # Cursor hooks
    links:
      hooks.json: hooks.cursor.json
```

## Path syntax (applies file-wide)

| Form | Interpretation | Best for |
|------|----------------|----------|
| `~/xxx` | expands to the home directory | cross-project shared libraries |
| `./xxx`, `xxx` | resolved from **the directory containing agsy.yaml** (not your current directory) | in-project libraries |
| `/abs/path` | used as is | special layouts |

`~` expands to **your own** home directory only; the shell's `~user` form (another user's home) is not supported and is rejected with an error rather than silently misread as `$HOME/user`.

Because relative paths resolve against the config file's location, running agsy from a project **subdirectory** works normally — agsy searches upward for `agsy.yaml` the way git does (the one exception is `init`, which only looks at the current directory so you control exactly where the config is created).

## `version`

Config format version, currently `2` (since v0.2.0). Omitted = current. A `version: 1` file still loads (fields were only added), but it must gain `on_conflict.hooks` (see the upgrade notes). A file whose version exceeds what the running agsy supports triggers an upgrade request — a config with `merge` must not be executed by a version that does not understand merge.

## `sources` (required, at least one)

- An ordered array — **order is priority**: with `on_conflict: first`, the same-name item from the earlier source survives; the concatenated `AGENTS.md` also follows this order.
- Common combination: `[~/shared-lib, ./project-lib]` — base content in the shared library, project-specific additions in the project one.
- A source missing some category subdirectory (e.g. no `workflows/`) is normal, not an error.
- When an entire source path is missing: `plan` still previews (marked incomplete), but `apply` **refuses to run** — never rebuild from an incomplete source list, or the missing source's items would be wiped.
- Sources must be **mutually distinct and non-nested**: the same path listed twice (in any spelling) or a source lying inside another is rejected at validation — the files would otherwise be collected twice.

### Source tags

Each source gets an auto-generated tag (used by `rename` and shown by `plan`): the last path segment with leading dots removed (`~/all-ai-lib` → `all-ai-lib`, `./.flow` → `flow`). When two sources' tags clash, agsy merges in parent directory names level by level, and appends a number only if they are still identical — tags are guaranteed unique.

## `build.out` (output directory)

Default `.agsy`. **`apply` empties this directory on every run and `clean` deletes it entirely**, so validation rejects dangerous values outright:

- the project root itself, or an ancestor of it (would wipe the whole project);
- anywhere **outside** the project (an unrelated directory is not disposable output);
- anything containing the home directory;
- anything containing, or contained in, a source (would delete originals).

In one sentence: **only a dedicated subdirectory inside the project.**

**Changing `out` requires a specific order**: first run `agsy clean` under the **old** config, then edit `agsy.yaml` and run `agsy apply`. In the reverse order the old output directory is left behind with nothing tracking it. Update `.gitignore` afterwards as well.

## `build.categories`

- `from`: the subdirectory scanned inside each source.
- `to`: the output subdirectory inside `.agsy/`.
- When only one half is set, the other half gets the default.
- **The four `from` values must differ, and so must the four `to` values**; no `to` may be `AGENTS.md` (reserved for the derived rules file) or one of `hooks.claude.json`, `hooks.codex.json`, `hooks.antigravity.json`, `hooks.cursor.json` (reserved for the hook registries).
- **When to change `from`**: an existing library whose subdirectory has a different name (say it has always been `prompts/`) can be connected without moving files via `from: prompts`. `to` rarely needs changing.

### Acceptance rules per category

Files that do not match the rules are **skipped and reported** (`plan` and `doctor` both list the reason) — nothing disappears silently:

| Rule | Notes |
|------|-------|
| names starting with `.` | always skipped (hidden files are not even reported, keeping `.DS_Store` out of the output) |
| symbolic links | **never collected**. The build copies file contents; a link could smuggle files from outside the source (e.g. a private key) into the mounted output |
| irregular files (FIFO, socket, device) | **never collected**. Reading a named pipe blocks forever, so one planted in a source would hang the build; a skill containing one is rejected entirely |
| rules / workflows | single `.md` files only; directories rejected; files over **5 MB** are skipped (an instruction file that large is never useful as context) |
| skills | **directories** only, and `SKILL.md` is mandatory; a skill containing **any symlink is rejected entirely** |
| hooks | **directories** only, and `hook.yaml` is mandatory; likewise rejected entirely on any symlink or irregular file. The directory name is the hook name and must be lowercase a–z, 0–9 and hyphens (others are normalized, noted by plan) |

## `build.on_conflict` (required per category)

What happens when several sources contain same-name items. **There is no implicit default** — a decision that determines which content survives must be made explicitly.

| Strategy | Behavior | Best for |
|----------|----------|----------|
| `rename` | keep both copies, filenames tagged with their source: `python-style.md` → `python-style-fromlib-all-ai-lib.md` | rules ("global base + project extras" often coexist) |
| `error` | stop and list the conflicts for manual resolution (most conservative) | skills (see below) |
| `first` | keep only the highest-priority copy, discard the rest (`plan` lists the discarded) | when "project overrides global" is certain |

### Why `error` rather than `rename` for skills?

Skills trigger on the semantics of the `SKILL.md` description — with two same-named skills coexisting, which one a tool picks is unpredictable. Skill names are also bound by the Agent Skills spec (lowercase a–z, 0–9, single hyphens, name equal to the directory name), so `rename` must rewrite the front-matter `name` as well as the directory (agsy does this automatically). A same-name skill usually means the two should be merged, so manual handling is the default recommendation.

### Why `error` for hooks too?

Two hooks with the same name are usually two versions of the same thing that should become one. `rename` still works (the directory name gains the source tag; Antigravity's top-level registry key follows).

### Collisions on final output paths

After `rename`, or by naming coincidence, two items' **final output paths** can still be identical — including across categories: a workflow named `deploy.md` derives the skill `skills/deploy`, which collides with a real skill named `deploy`. agsy always **blocks the build** in this case — never silent overwriting.

## `build.tools` (required)

The closed list of tool names a workflow's `target:` front matter may reference. `init` fills it from the adapters you select. A `target:` value not in this list is an error: `plan` lists them all, `apply` refuses to build — a typo must fail loudly rather than silently exclude the workflow everywhere.

Validation also keeps this list consistent with the mount configuration around workflows: a mount that links the workflows output requires `antigravity` (the only tool that reads that directory) to be listed here, and listing `antigravity` requires a workflows link somewhere — otherwise stubs would be built that no tool reads, or an always-empty directory would be mounted.

### Workflow `target:` front matter

```yaml
---
target: [claude, codex]   # or a single string: target: claude
---
```

- Absent → the workflow is for every tool in `build.tools`.
- Present → only the listed tools. Two effects: the skill form is produced when at least one listed tool is not `antigravity`; the `workflows/` form is produced when `antigravity` is listed (a redirect stub when a skill form exists, otherwise the full content).
- The skills output is one directory shared by several tools, so exclusion is coarse: a partial list still reaches every tool that mounts skills, and `plan` notes this.
- `target:` is an agsy field; the build strips it from every output's front matter.

## `hook.yaml` for hooks

Every hook directory contains one `hook.yaml`. Events and matchers use the Claude Code / Codex shape because it is the most general of the four; build translates it into each vendor's dialect.

```yaml
description: Block rm -rf and friends              # optional; shown by plan
target: [claude, codex, antigravity, cursor]       # optional; same semantics as workflows: omitted = all of build.tools
events:                                            # required; at least one event
  PreToolUse:                                      # generic event name (table below)
    - matcher: Bash                                # optional; defaults to Claude / Codex tool names
      hooks:                                       # required; at least one handler
        - type: command                            # optional; defaults to command
          command: ./block-rm.sh                   # required for command; relative to this hook directory
          timeout: 10                              # optional; other fields pass through
      overrides:                                   # optional; per-tool differences
        antigravity: { matcher: run_command }
        cursor:      { matcher: Shell }
```

**Generic event names** (Claude Code / Codex naming; "—" means the vendor documents no such hook, so it is skipped there and noted by plan):

| Generic | claude | codex | antigravity | cursor |
|---|---|---|---|---|
| `PreToolUse` | ✓ | ✓ | ✓ | `preToolUse` |
| `PostToolUse` | ✓ | ✓ | ✓ | `postToolUse` |
| `Stop` | ✓ | ✓ | ✓ | `stop` |
| `SessionStart` / `SessionEnd` | ✓ | ✓ | — | `sessionStart` / `sessionEnd` |
| `UserPromptSubmit` | ✓ | ✓ | — | `beforeSubmitPrompt` |
| `PermissionRequest` | ✓ | ✓ | — | — |
| `SubagentStart` / `SubagentStop` | ✓ | ✓ | — | `subagentStart` / `subagentStop` |
| `PreCompact` | ✓ | ✓ | — | `preCompact` |
| `PostCompact` | ✓ | ✓ | — | — |
| `Interrupt` | — | ✓ | — | — |
| `PostToolUseFailure` | ✓ | — | — | `postToolUseFailure` |
| `StopFailure` | ✓ | — | — | — |
| `PreInvocation` / `PostInvocation` | — | — | ✓ | — |

**Handler types**: claude supports all (command, http, mcp_tool, prompt, agent); codex only command and mcp_tool; antigravity only command; cursor only command and prompt. Unsupported handlers are skipped one by one and reported.

**Translation rules**:

1. Tools not listed in `target` do not receive the hook; plan notes which ones are left out. A `target` naming a tool from `build.tools` that has no registry format (anything besides the four built-in tools) is noted too: the hook does not reach it.
2. Events the vendor lacks and unsupported types are skipped and noted by plan; Antigravity honours a matcher on `PreToolUse` / `PostToolUse` only, a matcher on any other event is dropped with a note. When nothing at all applies to a tool its registry is still written (empty) so the link never dangles.
3. `overrides.<tool>` keys only need to be tools agsy knows (ignored when not in `build.tools`), so a shared library carrying overrides for all four vendors still works in a project serving one; an entirely unknown name is an error. `matcher` overrides the group's matcher; `hooks[i]` overrides fields of the i-th handler — an index past the group's handlers, or an override that leaves a command handler without a `command`, is an error (apply refuses). An override that changes a handler's `type` away from `command` drops the `command` field for that tool, with a note.
4. **Path rewriting**: every whitespace-separated token of `command` starting with `./` becomes an **absolute path** into `.agsy/hooks/<name>/…`; the rest of the string is kept as written (`python3 ./check.py` works). The command runs through a shell, so a rewritten path is **quoted** when it contains spaces or shell metacharacters (a project under `My Projects/`); a plain path stays unquoted. Do **not** quote a `./` path yourself (`"./x.sh"` is refused): build adds quotes when needed. A referenced file that does not exist makes apply refuse, in main handlers and in `overrides` alike. The registry holds this machine's absolute paths; every machine runs its own apply.
5. Other handler fields pass through verbatim (three vendors share the shape); Cursor's flat shape keeps only `timeout`, `failClosed`, `loop_limit` and `prompt`, dropping the rest with a note.

**agsy translates the registry layer, not the scripts.** The stdin JSON each vendor feeds a script differs (Claude / Codex use `tool_input.command`, Cursor and Antigravity have their own fields); a script meant for all four must branch on `hook_event_name` or the vendor's fields itself.

## `mount` (required, at least one)

- `dir`: where the links go; `.` means the project root. `links`: `link-name: top-level-output-name`.
- A link may target each category's `to` value, `AGENTS.md` (the derived rules file), or one of the four hook registries `hooks.<tool>.json` (that tool must be in `build.tools`). Targets are top-level only.
- Entries sharing a `dir` are merged (several adapters mount into `.agents`); a same-name link with a different target is an error.
- Validation also rejects: a `dir` inside the output (apply's wipe would take the links with it), a `dir` inside a source (the link would be scanned as source content), and link names containing path separators.
- **A `dir` outside the project directory requires an explicit `outside_project: true` on that mount entry.** This is a safety gate: without it, running `apply` on a cloned repository whose `agsy.yaml` mounts into your home directory (say `dir: ~/.claude`) would silently point your **global** tool configuration at that repository's content. Only opt in for configs you wrote yourself.
- Link implementation: macOS / Linux use **relative symlinks** for everything. Windows uses **junctions** for directories and **hard links** for the root `AGENTS.md` and the hook registries — neither needs administrator rights. Junctions store absolute paths: after moving the project, rerun `agsy apply`.

### `merge`: Claude Code only

```yaml
  - dir: .claude
    merge:
      settings.json: hooks.claude.json
```

Claude Code's hooks have no separate file: they live in the `hooks` key of `.claude/settings.json`, next to your permissions, model and other settings, so linking the whole file would swallow them. `merge` means "**own only the entries agsy wrote into the `hooks` key**":

- **Ownership**: a matcher group under `hooks` belongs to agsy when any of its handlers carries the display-only `statusMessage: "agsy:<hook name>"` or has a `command` pointing into `.agsy/hooks/` (the current output, or the one recorded in the manifest). Build sets the mark on every handler written for Claude Code; a `statusMessage` given in `hook.yaml` follows it (`agsy:block-rm · linting`). The mark is path-independent: groups of an earlier apply are recognised and replaced after the project is moved, after `build.out` is renamed, and when the command names no `./` path (`npm run lint`). Same logic as `IsManagedLink` (a link into the output is agsy's).
- **apply**: old agsy groups are removed, the registry's groups added; every other key and every other group is kept, in order (the whole file is re-indented with two spaces). Containers present before apply — an empty event array, a `hooks: {}` — are kept even when empty; the `hooks` key and event arrays apply introduced are removed when empty (recorded in the manifest). A missing file is created and recorded as agsy-created. With nothing to merge and nothing of agsy's in the file (state *idle*), the file is neither created nor rewritten.
- **status**: an edited agsy group is listed as an artifact-side change (apply asks, then rebuilds); a removed one as missing (apply restores). Your own groups are never an anomaly. A file recorded as a merge target that the mount config no longer names, still holding agsy groups, is reported as an **orphan**: apply never touches it, clean strips it.
- **clean**: agsy groups are removed from current and orphaned targets; the `hooks` key and event arrays apply introduced go with them, others stay; the file is deleted only if agsy created it and it is now empty. An idle target is not touched.
- **Refused**: a target that is a symlink (agsy never writes through links) or not a JSON object stops apply's pre-check and is skipped (and reported) by clean.
- The `merge` value can only be `hooks.claude.json` or `hooks.codex.json` (merge reads back only that shape), and the tool must be in `build.tools`; `merge` and `links` in one `dir` may not share a name; one registry cannot be both linked and merged; a `dir` carrying merge entries must lie inside the project; `outside_project: true` does not apply to merge. agsy owns the project-level file only; user-level files such as `~/.claude/settings.json` stay the user's (next paragraph).
- A mount entry with only `merge` and no `links` is valid.

Put your own Claude hooks in `.claude/settings.local.json` or `~/.claude/settings.json` — Claude Code stacks its settings layers rather than replacing them. The same holds for the other vendors: `~/.codex/hooks.json`, `~/.cursor/hooks.json`, `~/.gemini/config/` (Antigravity does not document its merge behaviour; test it).

### The reverse check is only a hint

Linking `hooks.<tool>.json` while `tool` is not in `build.tools` is an error (the file would stay empty forever). The reverse — `tool` listed but its registry not mounted — is **not** an error, so existing projects keep working after upgrading; `plan` and `doctor` print a ⚠ when the sources actually contain hooks.

## Validation error quick reference

Problems are reported under a "config validation failed" header, **all at once**. Common messages:

| Error message | Fix |
|---------------|-----|
| `sources is not set; at least one source path is required` | add at least one source |
| `build.on_conflict.rules is not set, please explicitly choose first / rename / error` | set the strategy for all four categories |
| `build.on_conflict.hooks is not set (new in v0.2.0)…` | upgrading from v0.1: add `hooks: error`, or rerun `agsy init` |
| `build.categories.x.to must not be "hooks.codex.json"…` | that name is reserved for a registry; pick another |
| `mount … merge.settings.json points to "z", but only a hook registry of the claude / codex shape can be merged` | merge targets are `hooks.claude.json` or `hooks.codex.json` only |
| `mount dir … resolves outside the project directory (…), but it carries merge entries` | merge targets must be inside the project; personal hooks go in the tool's user-level file |
| `mount … links.hooks.json points to "hooks.cursor.json", but build.tools does not list "cursor"` | add `cursor` to `build.tools` or drop the link |
| `build.tools is not set; list the tools this project serves…` | list the tools, e.g. `[claude, codex, antigravity, cursor]` |
| `build.out (…) is not inside the project directory (…)` | point out back to a dedicated in-project directory (e.g. `.agsy`) |
| `build.categories.x.to and y are both "…"` | give one of them a different `to` |
| `mount … links.x points to "z", but the output has no such top level` | the target must be a category's `to` value, `AGENTS.md` or a registry file |
| `sources … resolve to the same directory` / `… are nested` | list each source once; un-nest them |
| `mount dir … resolves outside the project directory` | intentional? add `outside_project: true` to that mount entry |
| `a mount links to the workflows output …, but build.tools does not list "antigravity"` | add `antigravity` to `build.tools` or drop the workflows link |
| `version: N exceeds the maximum … supported by this agsy` | the config came from a newer agsy — upgrade |
