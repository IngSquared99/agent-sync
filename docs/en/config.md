# Configuration: the agsy.yaml Reference

`agsy.yaml` is agsy's only configuration file. It lives at the project root and **should be version-controlled** (the artifact directory `.agsy/` should not).
It is normally generated by the `agsy init` questionnaire; this chapter explains every field so you can edit it by hand with confidence.

## Complete example

```yaml
# agsy config file (agent-sync)
# Path syntax: ~ prefix = home expansion; relative = resolved from this file's directory; absolute = as is
version: 1

sources:                      # ordered array, earlier entries win
  - ~/all-ai-lib
  - ./repo-ai-lib

build:
  out: .agsy                  # must be inside the project (apply wipes it entirely)

  categories:                 # source subdir → output subdir (the three "to" values must differ)
    rules:     { from: rules, to: rules }
    skills:    { from: skills, to: skills }
    workflows: { from: workflows, to: workflows }

  on_conflict:                # same-name handling: first / rename / error (required per category)
    rules:     rename
    skills:    error
    workflows: rename

  route:                      # workflow routing
    field: target             # which front-matter field to read
    default: [claude, codex]  # buckets for workflows without a target
    buckets: [claude, codex]  # all valid buckets

mount:
  - dir: .claude              # Claude Code
    links:
      rules:    rules
      skills:   skills
      commands: workflows/claude
  - dir: .codex               # OpenAI Codex
    links:
      prompts:  workflows/codex
```

## Path syntax (applies file-wide)

| Form | Interpretation | Best for |
|------|----------------|----------|
| `~/xxx` | expands to the home directory | cross-project shared libraries |
| `./xxx`, `xxx` | resolved from **the directory containing agsy.yaml** (not your current directory) | in-project libraries |
| `/abs/path` | used as is | special layouts |

Because relative paths resolve against the config file's location, running agsy from a project **subdirectory** works normally — agsy searches upward for `agsy.yaml` the way git does (the one exception is `init`, which only looks at the current directory so you control exactly where the config is created).

## `version`

Config format version, currently `1`. Omitted = 1. A file whose version exceeds what the running agsy supports triggers an upgrade request (an old program must not misread a newer format with old rules).

## `sources` (required, at least one)

- An ordered array — **order is priority**: with `on_conflict: first`, the same-name item from the earlier source survives.
- Common combination: `[~/shared-lib, ./project-lib]` — base content in the shared library, project-specific additions in the project one.
- A source missing some category subdirectory (e.g. no `workflows/`) is normal, not an error.
- When an entire source path is missing: `plan` still previews (marked incomplete), but `apply` **refuses to run** — never rebuild from an incomplete source list, or the missing source's items would be wiped.

### Source tags

Each source gets an auto-generated tag (used by `rename` and shown by `plan`): the last path segment with leading dots removed (`~/all-ai-lib` → `all-ai-lib`, `./.flow` → `flow`). When two sources' tags clash, agsy merges in parent directory names level by level (`b-flow`), and appends a number only if they are still identical — tags are guaranteed unique.

## `build.out` (artifact directory)

Default `.agsy`. **`apply` empties this directory on every run and `clean` deletes it entirely**, so validation rejects dangerous values outright:

- the project root itself, or an ancestor of it (would wipe the whole project);
- anywhere **outside** the project (e.g. `~/Documents` — an unrelated directory is not disposable output);
- anything containing the home directory;
- anything containing, or contained in, a source (would delete originals).

In one sentence: **only a dedicated subdirectory inside the project.**

**Changing `out` requires a specific order**: first run `agsy clean` under the **old** config (removing the old links and artifacts), then edit `agsy.yaml` and run `agsy apply`. In the reverse order the old artifact directory is left behind with nothing tracking it (agsy only knows the currently configured out). Update `.gitignore` afterwards as well.

## `build.categories`

```yaml
categories:
  rules:     { from: rules, to: rules }
  skills:    { from: skills, to: skills }
  workflows: { from: workflows, to: workflows }
```

- `from`: the subdirectory scanned inside each source.
- `to`: the output subdirectory inside the artifacts.
- When only one half is set, the other half gets the default.
- **The three `to` values must differ** (otherwise single files from rules and directories from skills would share one level, overwriting same-name entries undetectably).
- `from` and `to` default to the same name. **When to change `from`**: an existing library whose subdirectory has a different name (say it has always been `prompts/`) can be connected without moving files via `from: prompts` — the escape hatch for the [naming convention](overview.md#source-directories-must-follow-the-naming-convention). `to` rarely needs changing.

### Acceptance rules per category

Files that do not match the rules are **skipped and reported** (`plan` and `doctor` both list the reason) — nothing disappears silently:

| Rule | Notes |
|------|-------|
| names starting with `.` | always skipped (hidden files are not even reported, keeping `.DS_Store` out of the output) |
| symbolic links | **never collected**. The build copies file contents; a link could smuggle files from outside the source (e.g. a private key) into the mounted artifacts |
| rules / workflows | single `.md` files only; directories rejected |
| skills | **directories** only, and `SKILL.md` is mandatory (a directory without it counts as assets/drafts); a skill containing **any symlink is rejected entirely** |

## `build.on_conflict` (required per category)

What happens when several sources contain same-name items. **There is no implicit default** — this is deliberate: a decision that determines which content survives must be made explicitly.

| Strategy | Behavior | Best for |
|----------|----------|----------|
| `rename` | keep both copies, filenames tagged with their source: `python-style.md` → `python-style-fromlib-all-ai-lib.md` | rules ("global base + project extras" often coexist) |
| `error` | stop and list the conflicts for manual resolution (most conservative) | skills (see below) |
| `first` | keep only the highest-priority copy, discard the rest (`plan` lists the discarded) | when "project overrides global" is certain |

### Why `error` rather than `rename` for skills?

Skills trigger on the semantics of the `SKILL.md` description — with two same-named skills coexisting, which one a tool picks is unpredictable. Skill names are also bound by the Agent Skills spec (lowercase a–z, 0–9, single hyphens, name equal to the directory name), so `rename` must rewrite the front-matter `name` as well as the directory (agsy does this automatically and restores it on promote). A same-name skill usually means the two should be merged, so manual handling is the default recommendation.

### Collisions after rename

After `rename`, or by naming coincidence, two items' **final output names** can still be identical (e.g. `God-Lib` and `god-lib` sanitize to the same name). agsy always **blocks the build** in this case — never silent overwriting.

## `build.route` (workflow routing)

```yaml
route:
  field: target             # which front-matter field to read
  default: [claude, codex]  # buckets for untargeted workflows; [] = place nowhere and warn
  buckets: [claude, codex]  # list of all valid buckets (required)
```

- A workflow writes `target: claude` (single) or `target: [claude, codex]` (multiple) in its front matter; the build copies it into the matching `workflows/<bucket>/` directories.
- A `target` value not present in `buckets` = **routing error**: `plan` lists them all, `apply` refuses to build.
- With `default: []`, untargeted workflows are **placed in no bucket** and `plan`/`apply` warn. A default covering all buckets is recommended: "appears everywhere" beats "mysteriously missing".
- `buckets` is normally assembled by `init` from the selected adapters; hand-added buckets survive init's edit mode.

## `mount` (required, at least one)

```yaml
mount:
  - dir: .claude            # mount directory (typically a tool's config dir)
    links:
      rules:    rules              # .claude/rules   → .agsy/rules
      skills:   skills             # .claude/skills  → .agsy/skills
      commands: workflows/claude   # .claude/commands → .agsy/workflows/claude
```

- `dir`: where the links go; `links`: `link-name: relative-target-inside-artifacts`.
- The target's first level must be some category's `to` value; **only workflows may have a second level** (a bucket, which must exist in `route.buckets`); nothing deeper.
- Validation also rejects: the same `dir` appearing twice, a `dir` inside the artifact directory (apply's wipe would take the links with it), a `dir` inside a source (the link would be scanned as source content).
- Link implementation: macOS / Linux use **relative symlinks** (moving the whole project keeps them valid); Windows uses **junctions** (no administrator rights, but they store absolute paths — rerun `agsy apply` after moving the project).

The built-in adapters' mount combinations are listed in the [Adapters chapter](adapters.md); a tool not on the list gets its own hand-written mount entry, which init's edit mode preserves as is.

## Validation error quick reference

When the config has problems, they are reported under a "config validation failed" header, **all at once** (not one per run). Common messages (English interface shown; the Chinese interface has matching text):

| Error message | Fix |
|---------------|-----|
| `sources is not set; at least one source path is required` | add at least one source |
| `build.on_conflict.rules is not set, please explicitly choose first / rename / error` | set the strategy for all three categories |
| `build.out (…) is not inside the project directory (…). apply wipes it entirely…` | point out back to a dedicated in-project directory (e.g. `.agsy`) |
| `build.categories.x.to and y are both "…"; different categories must output to different subdirectories` | give one of them a different `to` |
| `mount … links.x points to "z", but the output has no such top level, valid values: […]` | the first level must be some category's `to` value (rules / skills / workflows) |
| `mount … links.x points to bucket "b", but it is not in build.route.buckets` | add the bucket to `route.buckets` or change the target |
| `mount is not set; at least one mount target is required` | mount at least one tool |
| `version: N exceeds the maximum … supported by this agsy, please upgrade agsy` | the config came from a newer agsy — upgrade |
