# Configuration: the agsy.yaml Reference

`agsy.yaml` is agsy's only configuration file. It lives at the project root and **should be version-controlled** (the output directory `.agsy/` should not).
It is normally generated by the `agsy init` questionnaire; this chapter explains every field so you can edit it by hand with confidence.

## Complete example

```yaml
# agsy config file (agent-sync)
# Path syntax: ~ prefix = home expansion; relative = resolved from this file's directory; absolute = as is
version: 1

sources:                      # ordered array, earlier entries win
  - ~/all-ai-lib
  - ./repo-ai-lib

build:
  out: .agsy                  # must be inside the project (apply wipes it entirely)

  categories:                 # source subdir → output subdir (from / to values must each differ)
    rules:     { from: rules, to: rules }
    skills:    { from: skills, to: skills }
    workflows: { from: workflows, to: workflows }

  on_conflict:                # same-name handling: first / rename / error (required per category)
    rules:     rename
    skills:    error
    workflows: rename

  tools: [claude, codex, antigravity, cursor]   # valid values for a workflow's target: front matter

mount:
  - dir: .                    # project root: AGENTS.md for Codex / Cursor / Antigravity
    links:
      AGENTS.md: AGENTS.md
  - dir: .claude              # Claude Code
    links:
      rules:  rules
      skills: skills
  - dir: .agents              # Codex + Antigravity + Cursor
    links:
      skills:    skills
      workflows: workflows
```

## Path syntax (applies file-wide)

| Form | Interpretation | Best for |
|------|----------------|----------|
| `~/xxx` | expands to the home directory | cross-project shared libraries |
| `./xxx`, `xxx` | resolved from **the directory containing agsy.yaml** (not your current directory) | in-project libraries |
| `/abs/path` | used as is | special layouts |

`~` expands to **your own** home directory only; the shell's `~user` form (another user's home) is not supported and is rejected with an error rather than silently misread as `$HOME/user`.

Because relative paths resolve against the config file's location, running agsy from a project **subdirectory** works normally — agsy searches upward for `agsy.yaml` the way git does (the one exception is `init`, which only looks at the current directory so you control exactly where the config is created).

## `version`

Config format version, currently `1`. Omitted = 1. A file whose version exceeds what the running agsy supports triggers an upgrade request.

## `sources` (required, at least one)

- An ordered array — **order is priority**: with `on_conflict: first`, the same-name item from the earlier source survives; the concatenated `AGENTS.md` also follows this order.
- Common combination: `[~/shared-lib, ./project-lib]` — base content in the shared library, project-specific additions in the project one.
- A source missing some category subdirectory (e.g. no `workflows/`) is normal, not an error.
- When an entire source path is missing: `plan` still previews (marked incomplete), but `apply` **refuses to run** — never rebuild from an incomplete source list, or the missing source's items would be wiped.
- Sources must be **mutually distinct and non-nested**: the same path listed twice (in any spelling) or a source lying inside another is rejected at validation — the files would otherwise be collected twice.

### Source tags

Each source gets an auto-generated tag (used by `rename` and shown by `plan`): the last path segment with leading dots removed (`~/all-ai-lib` → `all-ai-lib`, `./.flow` → `flow`). When two sources' tags clash, agsy merges in parent directory names level by level, and appends a number only if they are still identical — tags are guaranteed unique.

## `build.out` (output directory)

Default `.agsy`. **`apply` empties this directory on every run and `clean` deletes it entirely**, so validation rejects dangerous values outright:

- the project root itself, or an ancestor of it (would wipe the whole project);
- anywhere **outside** the project (an unrelated directory is not disposable output);
- anything containing the home directory;
- anything containing, or contained in, a source (would delete originals).

In one sentence: **only a dedicated subdirectory inside the project.**

**Changing `out` requires a specific order**: first run `agsy clean` under the **old** config, then edit `agsy.yaml` and run `agsy apply`. In the reverse order the old output directory is left behind with nothing tracking it. Update `.gitignore` afterwards as well.

## `build.categories`

- `from`: the subdirectory scanned inside each source.
- `to`: the output subdirectory inside `.agsy/`.
- When only one half is set, the other half gets the default.
- **The three `from` values must differ, and so must the three `to` values**; no `to` may be `AGENTS.md` (reserved for the derived rules file).
- **When to change `from`**: an existing library whose subdirectory has a different name (say it has always been `prompts/`) can be connected without moving files via `from: prompts`. `to` rarely needs changing.

### Acceptance rules per category

Files that do not match the rules are **skipped and reported** (`plan` and `doctor` both list the reason) — nothing disappears silently:

| Rule | Notes |
|------|-------|
| names starting with `.` | always skipped (hidden files are not even reported, keeping `.DS_Store` out of the output) |
| symbolic links | **never collected**. The build copies file contents; a link could smuggle files from outside the source (e.g. a private key) into the mounted output |
| irregular files (FIFO, socket, device) | **never collected**. Reading a named pipe blocks forever, so one planted in a source would hang the build; a skill containing one is rejected entirely |
| rules / workflows | single `.md` files only; directories rejected; files over **5 MB** are skipped (an instruction file that large is never useful as context) |
| skills | **directories** only, and `SKILL.md` is mandatory; a skill containing **any symlink is rejected entirely** |

## `build.on_conflict` (required per category)

What happens when several sources contain same-name items. **There is no implicit default** — a decision that determines which content survives must be made explicitly.

| Strategy | Behavior | Best for |
|----------|----------|----------|
| `rename` | keep both copies, filenames tagged with their source: `python-style.md` → `python-style-fromlib-all-ai-lib.md` | rules ("global base + project extras" often coexist) |
| `error` | stop and list the conflicts for manual resolution (most conservative) | skills (see below) |
| `first` | keep only the highest-priority copy, discard the rest (`plan` lists the discarded) | when "project overrides global" is certain |

### Why `error` rather than `rename` for skills?

Skills trigger on the semantics of the `SKILL.md` description — with two same-named skills coexisting, which one a tool picks is unpredictable. Skill names are also bound by the Agent Skills spec (lowercase a–z, 0–9, single hyphens, name equal to the directory name), so `rename` must rewrite the front-matter `name` as well as the directory (agsy does this automatically). A same-name skill usually means the two should be merged, so manual handling is the default recommendation.

### Collisions on final output paths

After `rename`, or by naming coincidence, two items' **final output paths** can still be identical — including across categories: a workflow named `deploy.md` derives the skill `skills/deploy`, which collides with a real skill named `deploy`. agsy always **blocks the build** in this case — never silent overwriting.

## `build.tools` (required)

The closed list of tool names a workflow's `target:` front matter may reference. `init` fills it from the adapters you select. A `target:` value not in this list is an error: `plan` lists them all, `apply` refuses to build — a typo must fail loudly rather than silently exclude the workflow everywhere.

Validation also keeps this list consistent with the mount configuration around workflows: a mount that links the workflows output requires `antigravity` (the only tool that reads that directory) to be listed here, and listing `antigravity` requires a workflows link somewhere — otherwise stubs would be built that no tool reads, or an always-empty directory would be mounted.

### Workflow `target:` front matter

```yaml
---
target: [claude, codex]   # or a single string: target: claude
---
```

- Absent → the workflow is for every tool in `build.tools`.
- Present → only the listed tools. Two effects: the skill form is produced when at least one listed tool is not `antigravity`; the `workflows/` form is produced when `antigravity` is listed (a redirect stub when a skill form exists, otherwise the full content).
- The skills output is one directory shared by several tools, so exclusion is coarse: a partial list still reaches every tool that mounts skills, and `plan` notes this.
- `target:` is an agsy field; the build strips it from every output's front matter.

## `mount` (required, at least one)

- `dir`: where the links go; `.` means the project root. `links`: `link-name: top-level-output-name`.
- A link may target each category's `to` value, or `AGENTS.md` (the derived rules file). Targets are top-level only.
- Entries sharing a `dir` are merged (several adapters mount into `.agents`); a same-name link with a different target is an error.
- Validation also rejects: a `dir` inside the output (apply's wipe would take the links with it), a `dir` inside a source (the link would be scanned as source content), and link names containing path separators.
- **A `dir` outside the project directory requires an explicit `outside_project: true` on that mount entry.** This is a safety gate: without it, running `apply` on a cloned repository whose `agsy.yaml` mounts into your home directory (say `dir: ~/.claude`) would silently point your **global** tool configuration at that repository's content. Only opt in for configs you wrote yourself.
- Link implementation: macOS / Linux use **relative symlinks** for everything. Windows uses **junctions** for directories and **hard links** for the root `AGENTS.md` — neither needs administrator rights. Junctions store absolute paths: after moving the project, rerun `agsy apply`.

## Validation error quick reference

Problems are reported under a "config validation failed" header, **all at once**. Common messages:

| Error message | Fix |
|---------------|-----|
| `sources is not set; at least one source path is required` | add at least one source |
| `build.on_conflict.rules is not set, please explicitly choose first / rename / error` | set the strategy for all three categories |
| `build.tools is not set; list the tools this project serves…` | list the tools, e.g. `[claude, codex, antigravity, cursor]` |
| `build.out (…) is not inside the project directory (…)` | point out back to a dedicated in-project directory (e.g. `.agsy`) |
| `build.categories.x.to and y are both "…"` | give one of them a different `to` |
| `mount … links.x points to "z", but the output has no such top level` | the target must be a category's `to` value or `AGENTS.md` |
| `sources … resolve to the same directory` / `… are nested` | list each source once; un-nest them |
| `mount dir … resolves outside the project directory` | intentional? add `outside_project: true` to that mount entry |
| `a mount links to the workflows output …, but build.tools does not list "antigravity"` | add `antigravity` to `build.tools` or drop the workflows link |
| `version: N exceeds the maximum … supported by this agsy` | the config came from a newer agsy — upgrade |
