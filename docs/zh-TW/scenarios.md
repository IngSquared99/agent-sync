# 情境指南：apply 的每一種狀況

兩端不一致時究竟會發生什麼、防護什麼時候介入——本章以對照表列出所有情境。不確定時，先跑唯讀的 `agsy status`，把輸出對回本章。

## 基準：manifest 怎麼知道「是誰改的」

每次 `apply`，manifest（`.agsy/.agsy-manifest.json`）為每個項目記下兩種指紋：

```
                       ┌── SrcHash：建置當下來源的指紋
 建置時的快照 ──────────┤
                       └── 每個輸出各一個 hash（原樣複製與轉換產物一視同仁）

 之後的任何時刻：
   目前的來源  vs  SrcHash      不同 → 來源變了     （清單 A → apply 同步它）
   目前的輸出  vs  它的 hash    不同 → 產物端變了    （清單 B → apply 捨棄它）
```

建置時的快照是第三個參考點，讓 agsy 能說出**是誰**改了東西，而不只是「兩端不同」。

## 主矩陣：來源端 × 產物端

「產物端」是你或 AI 工具透過掛載連結（`.claude/`、`.agents/`、根目錄 `AGENTS.md`）實際碰到的東西——也就是 `.agsy/` 裡的檔案。

| # | 來源端 | 產物端 | status 顯示 | apply |
|---|--------|--------|------------|-------|
| 1 | 沒變 | 沒變 | （無落差） | 重建，內容相同 |
| 2 | **被改** | 沒變 | 清單 A：更新 | ✅ 重建，所有工具拿到新內容 |
| 3 | 沒變 | **被改** | 清單 B：修改，附保留指引 | ⚠ 列出，詢問「捨棄並重建?」 |
| 4 | **被改** | **被改** | 清單 A＋清單 B | ⚠ 同樣的確認；同意後以來源版為準 |
| 5 | **新增檔案** | — | 清單 A：新增 | ✅ 收進產物 |
| 6 | — | **新增檔案** | 清單 B：未追蹤，「搬進某個來源」 | ⚠ 列出，確認後**刪除** |
| 7 | **刪除檔案** | 沒變 | 清單 A：移除 ⚠（轉換形態一併消失） | 該項目從所有工具消失（status 事先警告過） |
| 8 | **整個來源路徑不存在**（沒 clone／磁碟沒掛／打錯字） | 任意 | ⚠ 來源路徑不存在（與「檔案被刪」明確區分） | ✘ **整個拒絕**——絕不以殘缺清單重建 |
| 9 | 沒變 | **產物副本被刪** | 產物缺失 | ✅ 重建它 |
| 10 | — | **轉換產物被改**（AGENTS.md、轉接頭、workflow 的 skill 形態） | 清單 B：修改，指引指向來源檔 | ⚠ 詢問後重新產生 |

兩條通則涵蓋整張表：

1. **apply 永遠站在來源這邊**——重建讓產物回到來源的當前狀態，產物端的任何東西都會被覆蓋或刪除，但一定**先列出、先確認**（列 3、4、6、10）。
2. **保留產物端改動永遠是手動搬進來源。** 沒有回寫指令；status 為每一筆指出目的地。AI 產出的內容先經過你的手，才進入庫。

## 保留產物端改動：唯一的流程

未追蹤檔通常是 AI 工具透過掛載**新增**的檔案（例如它替你寫的新規則）。想保留：

```sh
# 從產物搬進某個來源的對應子目錄
mv .agsy/rules/new-rule.md ~/all-ai-lib/rules/
agsy apply     # 從此它是被追蹤的正式項目
```

**被修改**的已追蹤檔同理，只是改成把變更合併進既有的來源檔。被編輯的**轉換產物**則改它的產生來源：

| 被改的檔案 | 應該改的是 |
|-----------|-----------|
| `AGENTS.md`（根目錄或 `.agsy/` 裡） | 對應的來源 rule——每段都有 `<!-- agsy: rules/… -->` 標記 |
| `workflows/<名稱>.md`（轉接頭） | 來源的 workflow 檔 |
| workflow 的 skill 形態 `skills/<名稱>/SKILL.md` | 來源的 workflow 檔 |

什麼都不保留、直接 apply，確認清單會列出每筆改動，同意後捨棄。

## 掛載連結情境

掛載連結本身也可能出狀況——這是「通道」的問題，不是內容差異：

| 情境 | status 顯示 | 怎麼發生 | 處理 |
|------|------------|----------|------|
| 連結遺失 | ✘ 連結遺失 | 被手動刪除，或 apply 從未執行 | `agsy apply` 重建 |
| 連結指向別處 | ✘ 指向 …,不是目前設定的目標 | `build.out` 改了，或連結被動過 | `agsy apply` 重建 |
| 連結已斷（目標不見） | ✘ 目標不存在 | `.agsy/` 被刪，或專案被搬移（Windows junction 存絕對路徑） | `agsy apply` 重建 |
| 掛載點被**實體**目錄或檔案佔用 | ✘ 被佔用 | 工具目錄本來就有同名資料夾，或根目錄存在真實 `AGENTS.md` | ✘ apply **拒絕**且**絕不代刪**——把內容搬進來源（通常正是你想要的）或自行移除，再 apply |
| 孤兒連結 | ⚠ 設定已不再引用 | 先前 apply 建立、之後工具被移出 mount | apply 只回報；手動刪或交給 `agsy clean` |

## 讓 apply 在建置前就停下的條件

這些檢查刻意排在捨棄確認**之前**：

| 條件 | 訊息大意 | 處理 |
|------|---------|------|
| 任一來源路徑不存在 | 拒絕以殘缺清單重建 | 修好路徑（clone／掛磁碟／改錯字） |
| 掛載點被實體路徑佔用 | 拒絕並列出；絕不代刪 | 自行搬走或刪除 |
| workflow target 錯誤（未知工具名） | 列出待修檔案 | 修 front matter 或擴充 `build.tools` |
| 同名衝突（`on_conflict: error`） | 列出衝突組 | 改名或刪除一份 |
| 最終輸出路徑碰撞（含跨類別） | 列出碰撞組 | 改名其中一個 |
| manifest 損壞但 `.agsy/` 存在 | 內容無從得知 | ⚠ 重建前多一次確認 |
| manifest 比本 agsy 新 | 舊規則不可解析新資料 | 升級 agsy（或刪 `.agsy/` 重建） |

## 快速決策圖

```
 先跑 agsy status，然後：

 有產物端改動?
   ├─ 想留一些 ──▶ 逐筆搬入／合併進來源（指引會指名）──▶ agsy apply
   └─ 全部捨棄 ──▶ agsy apply（確認捨棄）

 只有來源異動／產物缺失? ──▶ agsy apply

 掛載異常?
   ├─ 被實體路徑佔用 ──▶ 搬走它 ──▶ agsy apply
   ├─ 孤兒連結 ──▶ 手動刪或 agsy clean
   └─ 其他（遺失／指錯／已斷）──▶ agsy apply

 來源路徑不存在? ──▶ 先修路徑（clone／掛磁碟／改錯字）；修好前什麼都別跑
```
