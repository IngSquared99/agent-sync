# C-4. 情境全覽：apply 與 promote 的每一種狀況

apply 和 promote 遇到「兩端不一致」時到底會做什麼、什麼時候會被防呆擋下——這一章把**所有情境**列成對照表。遇到不確定的狀況，先跑 `agsy status`（唯讀），再拿它的輸出對照本章。

## C-4-1. 判斷的基準：manifest 怎麼知道「誰改了」

每次 `apply` 建置時，manifest（`.agsy/.agsy-manifest.json`）會為每個項目記下**兩個指紋**：

```
                    ┌── SrcHash：建置當下「來源檔」的內容指紋
 建置當下拍快照 ──────┤
                    └── Hash   ：建置當下「產物複本」的內容指紋

 之後任何時刻：
   現在的來源檔  vs  SrcHash   不同 → 來源端改了（behind，該 apply）
   現在的產物檔  vs  Hash      不同 → 產物端改了（local changes，該 promote）
   兩個都不同              → 兩端都改了（要人工處理）
```

因為有「建置當下」這個第三方基準，agsy 能分辨「誰改的」，而不是只看到「兩邊不一樣」。

## C-4-2. 主對照表：來源端 × 產物端

「產物端」＝ `.agsy/` 裡的複本；你或 AI 工具透過 `.claude/` 等**掛載連結**碰到的就是這一份檔案（名詞定義見[核心概念](00-overview.md#開始前先認識幾個名詞)）。

| # | 來源端 | 產物端 | status 顯示 | apply 的行為 | promote 的行為 |
|---|--------|--------|-------------|--------------|----------------|
| 1 | 沒變 | 沒變 | （無落差） | 重建，內容不變 | 無事可做 |
| 2 | **內容改了** | 沒變 | `behind` | ✅ 重建，同步新內容 | 沒有改動可寫回 |
| 3 | 沒變 | **內容改了** | `local changes` | ⚠ 先列清單，問「捨棄並重建？」 | ✅ 寫回來源 |
| 4 | **內容改了** | **內容改了** | `local changes`＋⚠ 來源也改了 | ⚠ 問「捨棄並重建？」（產物端改動會消失） | ✘ **拒絕**——直接覆蓋會清掉來源的新內容，請人工合併（見 C-4-3） |
| 5 | **新增檔案** | — | `new` | ✅ 收進產物 | 與它無關 |
| 6 | — | **新增檔案** | `untracked` | ⚠ 列出並確認後**刪除**（重建=以來源為準） | ✘ 寫不回——它沒有對應的來源位置（見 C-4-4） |
| 7 | **檔案被刪** | 沒變 | `behind`＋⚠ 來源已刪 | 項目從產物**消失**（status 事先就警告過） | 沒有改動可寫回 |
| 8 | **檔案被刪** | **內容改了** | `local changes`＋⚠ 來源檔已刪 | ⚠ 問「捨棄？」，同意後項目消失 | ⚠ 明確問「**要重建來源檔嗎？**」，答應才寫 |
| 9 | **整個來源路徑不見**（沒 clone／碟未掛載／打錯字） | 任何狀態 | ⚠ 來源路徑不見（與「檔案被刪」明確區分） | ✘ **整個拒絕執行**——不從殘缺的來源清單重建，否則缺席來源的項目會被清光 | ✘ 拒絕該來源的項目——先修好路徑 |
| 10 | 沒變 | **產物複本被刪** | `missing artifacts` | ✅ 重建補回 | 沒有內容可寫回（不算 local change） |
| 11 | — | **多個 bucket 複本，改成「不同」內容** | `local changes`＋⚠ 多複本分歧 | ⚠ 問「捨棄？」 | ✘ 拒絕——哪份是對的要由人決定 |
| 12 | — | **多個 bucket 複本，改成「相同」內容** | `local changes`（算一項） | ⚠ 問「捨棄？」 | ✅ 寫回，並把所有複本同步成一致 |

三條通用規律，記住就不用背表：

1. **apply 永遠以來源為準**——重建就是「把產物變成來源現在的樣子」，所以產物端任何未寫回的東西都會被蓋掉／刪掉，但一定**先列清單問你**（第 3、4、6、8、11、12 列）。
2. **promote 只在「能安全寫回」時動手**——凡是會蓋掉來源新內容（4）、無處可寫（6、10）、或需要人做選擇（11）的情境，一律拒絕或改問你。
3. **「路徑不見」和「檔案被刪」是兩回事**（9 vs 7）——前者多半是環境問題（repo 沒 clone、外接碟沒掛），agsy 直接停下要你先修，絕不會當成「你刪了檔案」處理。

## C-4-3. 情境 4 手把手：兩端都改了怎麼辦

1. `agsy status` 找到那個項目，記下它的原始來源路徑（報告裡有印）。
2. 手動比對兩份：**來源檔**（如 `~/all-ai-lib/rules/x.md`）vs **產物檔**（如 `.agsy/rules/x.md`，從 `.claude/rules/x.md` 點進去的也是同一份）。
3. 把要保留的內容合併進**來源檔**（記住：來源是唯一真相）。
4. `agsy apply` 重建——基準重設，回到情境 1。

## C-4-4. 情境 6 手把手：想保留 untracked 檔案

untracked 通常是 AI 工具透過工具目錄在產物端直接**新建**的檔案（例如它幫你寫了一個新 rule）。想留下來：

```sh
# 把檔案從產物搬進某個來源的對應子目錄
mv .agsy/rules/new-rule.md ~/all-ai-lib/rules/
agsy apply     # 之後它就是正式項目，開始被追蹤
```

不搬就 apply 的話，會在確認清單裡看到它，同意後被刪除。

## C-4-5. 掛載連結的情境

掛載連結本身也可能出狀況——這不屬於兩端的內容差異，是「通道」本身的問題：

| 情境 | status 顯示 | 怎麼發生 | 處理 |
|------|-------------|----------|------|
| 連結不存在 | ✘ 連結不見 | 手動刪了、或還沒 apply 過 | `agsy apply` 重建 |
| 連結指錯地方 | ✘ 指向…非目前設定的目標 | 改過 `build.out`、或連結被動過 | `agsy apply` 重建 |
| 連結斷掉（目標不存在） | ✘ 目標不存在 | `.agsy/` 被刪、專案被搬移（Windows junction 存絕對路徑） | `agsy apply` 重建 |
| 掛載點被**真實**目錄／檔案佔用 | ✘ 被真實目錄佔用 | 該工具目錄本來就有同名資料夾 | ✘ apply **拒絕**且**絕不代刪**——把內容搬進來源（通常正是你要的）或自行備份後刪除，再 apply |
| 孤兒連結（orphan） | ⚠ 不再被設定引用 | 之前 apply 建過，後來你把該工具從 mount 拿掉 | apply 只回報不刪；手動刪或 `agsy clean` 一併清 |

## C-4-6. 建置開始前就會擋下 apply 的狀況

這些檢查刻意排在「確認捨棄改動」**之前**——不能讓你先同意丟掉改動、等建置跑完才發現這輪注定失敗：

| 狀況 | 訊息重點 | 處理 |
|------|----------|------|
| 任一來源路徑不存在 | 拒絕從殘缺清單重建 | 修好路徑（clone／掛載／改錯字） |
| 掛載點被真實目錄佔用 | 拒絕並列出，絕不代刪 | 手動搬走或刪除 |
| workflow 路由錯誤（target 指到不存在的 bucket） | 列出待修檔案 | 修 front-matter 或補 `route.buckets` |
| 同名衝突（`on_conflict: error`） | 列出衝突組 | 改名或刪除其中一份 |
| 最終輸出名撞名（collision） | 列出撞名組 | 改名（rename 後仍可能巧合撞名，一律擋下不互蓋） |
| manifest 壞掉但 `.agsy/` 還在 | 無從得知裡面有沒有你的改動 | ⚠ 多問一次確認才重建 |
| manifest 版本比 agsy 新 | 用舊規則解讀新格式太危險 | 升級 agsy（或刪掉 `.agsy/` 重建） |

## C-4-7. promote 的完整防呆清單

除了主表的內容判斷，promote 對「寫到哪裡」還有一整組安全檢查：

| 防呆 | 規則 |
|------|------|
| 寫回位置鎖定 | 只能寫進該項目**自己的格子**：`<設定的來源>/<類別子目錄>/<原始名稱>`——manifest 被竄改也無法把寫入導去別處 |
| `--to` 白名單 | 只能指向 `agsy.yaml` 裡**已設定**的來源；寫到別處＝脫離管理，直接拒絕 |
| 拒寫符號連結 | 寫回目標若是 symlink，拒絕（不穿透連結寫檔） |
| 專案外要多確認 | 目標在專案外（共用庫）時多問一次——會影響所有用到該庫的專案 |
| `--all --to` 不支援 | 整批改道會讓來源與 manifest 脫鉤 |
| 改名 skill 還原名稱 | 寫回時自動把 `SKILL.md` 的 `name` 還原成原始名稱（`-fromlib-…` 只屬於產物） |
| `--to` 改道提醒 | 舊來源那份還在，下次建置會出現新舊兩份同名——確認後手動刪舊的 |
| 寫回後更新基準 | 產物指紋與來源指紋同步刷新：這筆改動回到無落差，也不會誤判「來源也改了」；下一步執行 apply 完成重建 |

## C-4-8. 快速決策圖

```
 遇到狀況先跑 agsy status，然後：

 有 local changes？
   ├─ 想保留 ──▶ agsy promote ──▶ agsy apply
   ├─ 不想保留 ─▶ agsy apply（確認捨棄）
   └─ 顯示「來源也改了」──▶ 人工合併進來源（C-4-3）──▶ agsy apply

 有 untracked？
   ├─ 想保留 ──▶ 搬進來源子目錄（C-4-4）──▶ agsy apply
   └─ 不想保留 ─▶ agsy apply（確認刪除）

 只有 behind / new / missing artifacts？ ──▶ agsy apply

 掛載異常？
   ├─ 被真實目錄佔用 ──▶ 手動搬走 ──▶ agsy apply
   ├─ 孤兒連結 ──▶ 手動刪或 agsy clean
   └─ 其他（不見／指錯／斷掉）──▶ agsy apply

 來源路徑不見？ ──▶ 先修路徑（clone／掛載硬碟／改錯字），別急著跑任何指令
```
