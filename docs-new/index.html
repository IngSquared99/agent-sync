0. 核心概念：agsy 是什麼？

它解決的問題

當你同時使用多個 AI 開發工具（Claude Code、OpenAI Codex、Antigravity…），每個工具都有自己的指令檔目錄：Claude Code 讀 .claude/rules/、.claude/skills/、.claude/commands/；Codex 讀 .codex/prompts/；Antigravity 讀 .agents/。同一份規範得複製好幾份、改一處要同步好幾處，而且你可能還想把「個人共用的一套」和「專案專屬的一套」疊在一起用。

agsy（agent-sync）：把多個來源（sources）的指令檔合併建置成單一產物目錄（預設 .agsy/），再用目錄連結掛載進每個工具的讀取位置。改動時只改來源，跑一次 agsy apply，所有工具同時更新。

開始前，先認識幾個名詞

後面的說明會一直用到這些詞。先大概有個印象，讀起來就不會卡；中途忘記了，隨時回來這張表查。

名詞意思
source（來源）你維護的原始指令檔庫（sources 陣列），可以有多個
build out（產物）apply 建置出的目錄，預設 .agsy/。裡面全是複本，整個可以砍掉重建
mount（掛載）在各工具的目錄裡建立指向產物的「連結」
連結（symlink / junction）作業系統的「捷徑」：一個指向別處資料夾的入口，打開它等於打開目標資料夾，不會多存一份檔案
category（類別）指令檔的三種分類：rules（規則）、skills（技能）、workflows（工作流程）
bucket（桶子）產物裡 workflows/ 底下按工具分的子資料夾（如 claude、codex），一個工具掛一桶
routing（分流）建置時決定「每份 workflow 要進哪些桶」的過程，依據是檔案裡的 target 標記
manifest.agsy/.agsy-manifest.json，建置紀錄檔；agsy 靠它判斷「哪邊被改過」
source tag（來源標籤）同名檔案改名保留時附加的來源識別，如 -fromlib-all-ai-lib
adapter（適配器）內建的「各家工具掛載範本」，init 時用來產生掛載設定

untracked產物端新增、manifest 不認識的檔案（apply 會刪；要保留請搬回來源）
orphan（孤兒連結）之前的 apply 建立、但現在設定已不再引用的連結

兩端與通道：檔案內容只存在於兩端——「來源端」＝ sources 裡的原始檔、「產物端」＝ .agsy/ 裡的複本。掛載是連結，工具目錄（.claude/ 等）裡開啟的檔案即為產物端。連結本身稱「掛載連結」，只是通道、不儲存內容；通道的各種狀況見情境全覽 C-4-5。

三層架構

agsy 的世界只有三層、兩個動作。先看最簡化的版本：

 你維護的來源     ── ①建置（複製）──▶    產物目錄     ── ②掛載（連結）──▶   各 AI 工具的目錄
   sources                             .agsy/                           .claude/ .codex/ …
  • 來源（sources）：你真正維護、進版控的原始檔。可有多個，順序＝優先權。
  • 產物（build.out，預設 .agsy/）：整個目錄視為可重建的拋棄式產出——apply 每次清空重建，手寫的東西別直接放進去（除非打算用 promote 寫回）。
  • 掛載（mount）：在各工具目錄建立指向產物的連結；工具看到的是連結，內容都在 .agsy/。

接下來把 ① 和 ② 兩個動作分開看清楚。

動作①「建置」：把多個來源合併「複製」成一份

 ~/all-ai-lib/rules/python-style.md  ──┐
 ~/all-ai-lib/rules/git-commit.md    ──┤  複製、合併
 ./repo-ai-lib/rules/api-naming.md   ──┘
                                       ▼
                              .agsy/rules/python-style.md
                              .agsy/rules/git-commit.md
                              .agsy/rules/api-naming.md

這張圖的重點只有一個：產物裡的檔案是「複本」。來源可以散落在好幾個地方（個人共用庫、專案內的庫…），建置後全部集中成一份；也正因為是複本，整個 .agsy/ 隨時可以砍掉重建，不心疼。

動作②「掛載」：建一個「連結」，不是再複製一次

 .claude/rules   ────────── 連結（捷徑）──────────▶   .agsy/rules/
 （工具從這裡讀）                                    （檔案實際只存在這裡）

這張圖的重點也只有一個：.claude/rules 不是一個真的資料夾，而是一個連結（macOS / Linux 用 symlink，Windows 用 junction）——像捷徑一樣，打開它看到的就是 .agsy/rules/ 裡的內容。所以：同一份檔案不會佔兩份空間；.agsy/ 一更新，所有工具立刻看到新內容，不需要再做一次「同步」。

把兩個動作串起來：完整樣貌

前面兩個動作都懂了之後，一個掛載完成的專案整體長這樣（看不懂的話，回頭看上面兩張小圖即可）：

┌────────────────────┐
│  來源 sources       │  ~/all-ai-lib/       （個人共用庫，跨專案）
│ （你維護的原始檔）    │  ./repo-ai-lib/      （專案內的庫）
└─────────┬──────────┘
          │  ① agsy apply：掃描 → 合併 → 複製
          ▼
┌────────────────────┐
│  產物 build.out     │  .agsy/rules/
│ （可整個重建的複本）  │  .agsy/skills/
│                    │  .agsy/workflows/<bucket>/
└─────────┬──────────┘
          │  ② agsy apply：建立目錄連結（symlink / junction）
          ▼
┌────────────────────┐
│  掛載 mount         │  .claude/rules  → ../.agsy/rules
│ （各 AI 工具實際     │  .claude/skills → ../.agsy/skills
│   讀取的位置）       │  .codex/prompts → ../.agsy/workflows/codex
└────────────────────┘

三種類別（categories）

指令檔依用途分成三種類別，先弄懂它們各自是什麼：

  • rules（規則）：長期有效的規範或風格指引——coding style、命名慣例、commit 訊息格式……AI 工具會把它當成「隨時都要遵守的背景守則」讀進去。
  • skills（技能）：打包好的「一項能力」——一個目錄裝著說明（SKILL.md）加上可能附帶的腳本、範本等素材。工具依 SKILL.md 裡的描述，在遇到相關任務時自動取用。
  • workflows（工作流程）：一步一步的操作流程或常用指令——release 流程、code review SOP……在 Claude Code 裡會變成可以直接呼叫的斜線指令（/release 這種）。

來源目錄下就用三個同名子目錄存放，格式各有規定：

類別來源子目錄（預設）格式輸出位置
rulesrules/單一 .md 檔.agsy/rules/
skillsskills/目錄，內含 SKILL.md.agsy/skills/
workflowsworkflows/單一 .md，front-matter 可標 target.agsy/workflows/<bucket>/

一個典型的來源長這樣：

~/all-ai-lib/
├── rules/
│   ├── python-style.md
│   └── git-commit.md
├── skills/
│   └── code-review/
│       ├── SKILL.md
│       └── scripts/…
└── workflows/
    └── release.md        （front-matter: target: claude）

目前支援的工具與對應資料夾

掛載之後，三種類別會出現在各工具的哪個位置？內建適配器目前支援三個工具，對應關係如下（細節與自訂方式見 適配器說明）：

工具掛載目錄rulesskillsworkflows
Claude Code.claude/.claude/rules.claude/skills.claude/commands（成為斜線指令）
OpenAI Codex.codex/—（不掛載）—（不掛載）.codex/prompts
Antigravity.agents/.agents/rules.agents/skills.agents/workflows

表格裡的每一格都是一個連結，實際內容都在 .agsy/ 裡；Codex 依其慣例只讀 prompts，所以 rules 和 skills 沒有掛載位置（init 時若只勾 Codex 會特別警告這件事）。

來源目錄必須照規範命名

不管是個人共用庫（~/all-ai-lib）還是專案內的庫（./repo-ai-lib），裡面的子目錄都必須叫 rules/、skills/、workflows/（複數）——agsy 掃描時只認這三個名字，拼錯或用別的名字（如 rule/、my-rules/）的目錄會被直接跳過，檔案就「神祕消失」了。

✔ 正確                          ✘ 掃不到
~/all-ai-lib/rules/…            ~/all-ai-lib/rule/…
~/all-ai-lib/skills/…           ~/all-ai-lib/Skill/…
~/all-ai-lib/workflows/…        ~/all-ai-lib/wf/…

如果你的既有目錄真的叫別的名字，不必搬家：可以在 agsy.yaml 用 build.categories.<類別>.from 改掉掃描的子目錄名，詳見設定檔說明。不確定有沒有掃到時，跑 agsy doctor 立刻見分曉。

workflows 的分流：bucket 與 routing

rules 和 skills 建置後所有工具讀同一份；workflows 不一樣——每個工具的「指令／prompt」格式與用途不一定通用，所以產物裡的 workflows/ 又按工具分成子資料夾：

.agsy/workflows/
├── claude/        ←  Claude Code 專用（.claude/commands 掛的就是這裡）
└── codex/         ←  Codex 專用（.codex/prompts 掛的就是這裡）

先把兩個名詞接起來：

  • 這些子資料夾就叫 bucket（桶子）：一個工具一個桶，各工具只掛載自己的桶。
  • 建置時 agsy 決定「每份 workflow 該丟進哪些桶」的過程，就叫 routing（分流）。

分流的依據，是 workflow 檔案開頭 front-matter 的 target 標記：

 workflows/release.md （target: claude）          ──▶  只進 claude 桶 → 只有 Claude Code 看得到
 workflows/deploy.md  （target: [claude, codex]） ──▶  兩個桶各放一份 → 兩個工具都看得到
 workflows/note.md    （沒寫 target）             ──▶  依 route.default 的設定決定去向

target 的寫法就是在檔案最上方：

---
target: claude          # 只給 Claude Code
# 或 target: [claude, codex]  # 兩者都要
---
Release 流程說明…

沒寫 target 會怎樣？落入設定檔 route.default 指定的桶。建議把 default 設成「全部的桶」——一份檔案「到處都出現」比「神祕消失」容易理解得多。

雙向資料流：apply 與 promote

apply（正向）：來源 → 產物。平常的改動都走這條——改來源、跑 apply，所有工具同步更新：

 sources（你在這裡改檔案）
    │
    │  agsy apply（重新建置＋掛載）
    ▼
 .agsy/ ──連結──▶  所有工具立刻讀到新內容

promote（反向）：產物 → 來源。當你（或 AI 工具）直接改了產物端的檔案——因為掛載是連結，實際被改到的是 .agsy/ 裡的複本——就用 promote 把改動收回來源：

 .claude/skills/…（AI 工具直接改了這裡的檔案）
    ‖  掛載是連結，所以實際改到的是產物端（.agsy/ 裡的複本）
    │
    │  agsy promote（把改動寫回）
    ▼
 sources（改動被保存——下次 apply 重建時才不會被蓋掉）

agsy 用 .agsy/.agsy-manifest.json 記錄建置當下來源與產物的雜湊值，status 因此能精準區分「來源更新了還沒重建」（behind）、「產物端被改了還沒寫回」（local changes）、以及兩邊同時被改（需人工合併）。

設計上的安全底線

  1. 不碰真實檔案：掛載點若已被「真實目錄／檔案」佔用，一律報錯請你手動處理，絕不代為刪除。
  2. 同名策略必須明說：on_conflict 每類別必填，沒有隱含預設。
  3. 刪除前必先確認：偵測到未寫回的改動一定先問；非互動環境沒有 --yes 就取消。
  4. 產物目錄防呆：build.out 只能是專案內專用目錄，指到家目錄／來源／專案根都會被擋。
  5. 不收符號連結：避免透過連結把來源以外的檔案夾帶進產物。

A. 安裝說明

依你的作業系統選一種方式，都是一行指令：

方式平台指令事前需要
方式一：HomebrewmacOSbrew install ingsquared99/tap/agsy已裝 Homebrew
方式二：wingetWindows 10 / 11winget install IngSquared99.agsy不用，系統內建
方式三：Go 原始碼全平台（Linux 請走這條）go install …（見 A-3）已裝 Go

安全性說明：方式一、二安裝的是 GitHub Release 上的預編譯執行檔——由公開的 CI 流程從公開原始碼自動編譯，且 brew 的 cask 與 winget 的 manifest 都寫死了對應檔案的 SHA-256 校驗碼，下載內容可驗證、可稽核。方式三則是直接抓原始碼在你自己的電腦上編譯，完全不經過預編譯檔。agsy 本身零第三方相依套件（只用 Go 標準函式庫）。

A-1. 方式一：Homebrew（macOS）

macOS 安裝
$ brew install ingsquared99/tap/agsy
  • brew 會從 GitHub Release 下載對應你機器（Apple Silicon / Intel）的執行檔並校驗。
  • 安裝過程已處理 macOS 的隔離屬性，第一次執行不會跳「無法驗證開發者」的警告。
  • 還沒裝過 Homebrew？到官網 brew.sh 照首頁指示安裝（macOS 開發者的標準配備，裝一次終身受用）。

A-2. 方式二：winget（Windows）

Windows 安裝
> winget install IngSquared99.agsy
  • winget 是 Windows 10 / 11 內建的官方套件管理器，不用先裝任何東西，開終端機（PowerShell 或 cmd）直接打即可。
  • 裝完重開一個新的終端機視窗，再執行 agsy version 確認。

A-3. 方式三：從原始碼建置（全平台；Linux 請走這條）

需要 Go 1.22 以上（建議最新穩定版）。還沒有 Go：macOS brew install go、Windows winget install GoLang.Go、Linux 用發行版套件（如 apt install golang-go）或官網 go.dev/dl。

快速版——一行指令，Go 工具鏈自動抓原始碼、本機編譯、裝進 ~/go/bin/：

go install github.com/IngSquared99/agent-sync/cmd/agsy@latest

裝完若終端機找不到 agsy，是 ~/go/bin 不在 PATH（PATH＝終端機尋找指令的目錄清單）：

# macOS（預設 zsh）：加入設定檔後重開終端機；Linux（bash）改寫進 ~/.bashrc
echo 'export PATH="$HOME/go/bin:$PATH"' >> ~/.zshrc

完整版——適合想先檢視程式碼、或打算修改程式的人（另需 Git）：

git clone https://github.com/IngSquared99/agent-sync.git
cd agent-sync
go test ./...                # （可選）先跑測試確認環境正常
go build -o agsy ./cmd/agsy  # 產出 agsy 執行檔（Windows 為 agsy.exe）
mv agsy ~/go/bin/            # 放進任一在 PATH 裡的目錄

沒有其他框架或函式庫需求——不用 npm、不用 pip，go build 一行就是全部。

A-5. 介面語言：中文／英文怎麼決定

agsy 內建繁體中文與英文兩種介面，不用設定就會自動判斷。它啟動時依序檢查三個「環境變數」（環境變數＝作業系統層級的設定值，終端機裡的程式都讀得到），找到第一個有值的就用它：

 AGSY_LANG 有值嗎？ ──有──▶ 用它判斷
     │ 沒有
     ▼
 LC_ALL 有值嗎？    ──有──▶ 用它判斷
     │ 沒有
     ▼
 LANG 有值嗎？      ──有──▶ 用它判斷
     │ 沒有
     ▼
   英文

判斷規則只有一條：值以 zh 開頭（例如 zh_TW.UTF-8、zh-TW）→ 繁體中文；其他任何值 → 英文。

三個變數的分工：

  • LC_ALL、LANG：作業系統本來就有的語言設定，不是 agsy 的東西。台灣的 macOS / Linux 通常已經是 zh_TW.UTF-8，所以什麼都不用做，agsy 一開就是中文。
  • AGSY_LANG：agsy 專屬的開關，優先權最高，用來蓋過系統設定（例如系統是英文但你想看中文介面）。

想手動指定語言：

export AGSY_LANG=zh-TW    # 這個終端機視窗內，強制中文
export AGSY_LANG=en       # 強制英文

export 只對目前這個終端機視窗有效；想永久生效，把那一行加進 shell 設定檔（macOS 預設 zsh → ~/.zshrc），重開終端機後生效。

B. 快速上手：四步完成第一次同步

整條路只有四步，走完一遍大約 10 分鐘：

 Step 0        Step 1         Step 2         Step 3
 準備來源  ──▶  init 設定  ──▶  plan 預覽  ──▶  apply 建置＋掛載  ──▶ 🎉 所有工具同步完成
 （擺檔案）     （問答一次）     （唯讀確認）     （正式執行）

以下的終端機畫面都是示意（依實際版本可能略有差異），幫助你預期每一步會看到什麼。

B-1. 兩種操作方式

agsy 有雙入口：不帶參數是互動選單，帶參數直接執行。不想背指令，打 agsy 就對了：

agsy — 互動選單
$ agsy
agsy v1.2.3

  狀態：落後 0 │ 新增 2 │ 本地改動 1 │ 未追蹤 0 │ 產物缺失 0 │ 掛載異常 0

要做什麼?
  apply    重建產物並掛載      ⚠ 1 項本地改動，需先確認
  plan     預覽變更，不寫入

心智模型只有一條：來源是唯一的真相來源（source of truth）。正常改動改來源＋apply；不小心（或刻意讓 AI）改到產物端，就用 promote 收回來。

C-1. 個人設定檔：agsy.yaml

放在專案根目錄、建議進版控。通常由 agsy init 產生；以下逐欄說明，讓你能放心手改。

完整範例

# 路徑語法：~ 開頭＝家目錄；相對路徑＝以本檔所在目錄為基準；絕對路徑＝原樣
version: 1

sources:                      # 有序陣列，越前面優先權越高
  - ~/all-ai-lib
  - ./repo-ai-lib

build:
  out: .agsy                  # 必須在專案內（apply 會整個清空重建）

  categories:                 # 來源子目錄 → 產物子目錄（三個 to 不可相同）
    rules:     { from: rules, to: rules }
    skills:    { from: skills, to: skills }
    workflows: { from: workflows, to: workflows }

  on_conflict:                # 同名處理：first / rename / error（每類別必填）
    rules:     rename
    skills:    error
    workflows: rename

  route:                      # workflow 分流
    field: target
    default: [claude, codex]
    buckets: [claude, codex]

mount:
  - dir: .claude              # Claude Code
    links:
      rules:    rules
      skills:   skills
      commands: workflows/claude
  - dir: .codex               # OpenAI Codex
    links:
      prompts:  workflows/codex

路徑語法（全檔通用）

寫法解讀適合
~/xxx家目錄展開跨專案共用庫
./xxx以 agsy.yaml 所在目錄為基準（不是執行目錄）專案內的庫
/abs/path原樣使用特殊佈局

因此從專案子目錄執行也正常——agsy 像 git 一樣往上找設定檔（唯一例外：init 只看目前目錄）。

version

設定格式版本，目前 1；省略視為 1。檔案版本高於 agsy 支援上限時會被要求升級 agsy。

sources（必填，至少一個）

  • 順序＝優先權：first 策略保留排前面的來源。
  • 來源缺某類別子目錄是正常的；整個路徑不存在時 plan 仍可預覽（標明不完整），但 apply 拒絕執行。
  • 來源標籤：取路徑最後一段去掉開頭的點（~/all-ai-lib → all-ai-lib）；撞名時自動併入父目錄名、仍相同才加數字，保證唯一。

build.out（產物目錄）

預設 .agsy。apply 會整個清空、clean 會整個刪除，所以有嚴格防呆——指向專案根／上層、專案外、家目錄、與來源互相包含的設定都會直接被擋。一句話：只能是專案內的專用子目錄。

要改 out 的話，順序很重要：先在舊設定下跑 agsy clean（把舊連結和舊產物清乾淨），再改 agsy.yaml、跑 agsy apply。順序反過來的話，舊產物目錄會殘留在磁碟上沒人清（agsy 只認得目前設定的 out）。改完也記得更新 .gitignore。

build.categories

from＝來源掃描子目錄、to＝產物輸出子目錄；只寫一半另一半補預設；三個 to 必須互不相同。預設 from 和 to 同名，什麼時候會改 from：你的既有庫子目錄不叫標準名稱時（例如一直都叫 prompts/），改 from: prompts 就能不搬家直接接上——這是來源命名規範的逃生口。to 則幾乎不需要動。

收錄規則（不合規會被略過並回報，不會默默消失）

規則說明
. 開頭一律略過（隱藏檔不回報，避免 .DS_Store 洗版）
符號連結一律不收——建置複製「內容」，連結可能夾帶來源外的檔案（如私鑰）進被掛載的產物
rules / workflows只收單一 .md；目錄不收
skills只收目錄且必須含 SKILL.md；內部含任何符號連結則整個不收

build.on_conflict（每類別必填）

策略行為適合
rename兩份都留，檔名附來源標籤：python-style-fromlib-all-ai-lib.mdrules（全域基底＋專案補充常需並存）
error停止並列出衝突，人工處理（最保守）skills（見下）
first只留優先權最高的那份，其餘捨棄（plan 會列出）確定「專案覆蓋全域」時

為什麼 skills 建議 error？skill 靠描述語意觸發，同名並存時工具選哪個難預測；且 skill 名稱受 Agent Skills 規範限制（小寫 a-z0-9、單一連字號、與目錄同名），rename 還得改寫 front-matter 的 name（agsy 會自動做、promote 時自動還原）。同名 skill 通常代表該整併，所以預設請人工處理。

撞名（collision）：rename 後或名稱巧合使最終輸出名相同（如 God-Lib 與 god-lib 淨化後相同）時，一律擋下建置，不默默互蓋。

build.route（workflow 分流）

  • field：讀哪個 front-matter 欄位（預設 target）。
  • workflow 寫 target: claude 或 target: [claude, codex]，建置時複製到對應 workflows/<bucket>/。
  • 指到 buckets 沒有的值＝路由錯誤：plan 全列、apply 拒絕。
  • 沒標 target → 套 default；default: [] 則不放進任何 bucket 並警告。建議 default 涵蓋全部 bucket。

mount（必填，至少一個）

  • dir＝放連結的目錄；links＝連結名稱: 產物內相對目標。
  • 目標第一層必須是某類別的 to；只有 workflows 可有第二層 bucket（且須在 route.buckets 裡）；不能更深。
  • 也會擋：同一 dir 重複、dir 在產物目錄或來源目錄內。
  • 連結實作：macOS/Linux 用相對 symlink（專案搬移仍有效）；Windows 用 junction（免特權，但存絕對路徑——搬移專案後要重跑 apply）。

依序詢問：來源路徑 → 掛載哪些工具（多選，來自內建適配器）→ 三類別同名策略（必答）→ 產物目錄 → 無 target 的 workflow 去向。（問答的完整畫面示意與每題答法，見快速上手 B-4。）寫檔後：若有類別「會建置但沒工具掛載」會警告（例如只勾 Codex 時 rules/skills 沒人讀）；並詢問是否把產物目錄加進 .gitignore。

編輯模式（設定檔已存在）

  • 每題預帶目前值，按 Enter 保留原值；已掛載的工具預先勾選。
  • 手動加過的不會被洗掉：自訂 mount、手加的 bucket、改過的 categories 與 route.field 都原樣保留。
  • 寫入前顯示逐行 diff 並確認；沒變更就直接結束。

非互動環境

agsy init --yes ~/all-ai-lib ./repo-ai-lib

init 的核心是「策略必須由使用者明確選擇」，所以沒人能回答時預設取消；--yes＝明確同意建議預設（rules=rename、skills=error、workflows=rename），來源用參數傳。

唯讀agsy doctor

環境健檢，不做任何動作：

  1. 設定檔找得到、格式合法。
  2. 來源路徑存在與否（不存在＝✘）。
  3. 各來源各類別子目錄：缺目錄只是 ⚠；存在則統計會收錄的檔數——計數規則與 build 完全相同，並逐一列出被略過的檔案與原因。
  4. 各掛載點現況（可建立／已是連結／指錯或斷掉／被真實目錄佔用）。
  5. 連結能力實測：實際建一個暫時連結再刪掉（Windows 驗證 junction 可用、免特權）。

結尾統計 N errors, M warnings；有錯誤時 exit 1。適用：裝完驗證環境、「檔案為什麼沒被收」、換機後檢查。

唯讀agsy plan

把 apply 完整演練一遍、保證不寫入。輸出三段：

  • build 預覽：來源清單（優先權、存在狀態、標籤）；各類別收錄項目、誰被改名、workflow 分到哪些 bucket 及原因；被 first 捨棄的、被排除的（附原因）；擋路問題（同名衝突、最終名撞名、路由錯誤）一次全列。
  • mount 預覽：每個連結將建立／刪除重建／修復／或被真實目錄擋住（apply 會失敗）。
  • 摘要：項目數│改名│衝突│撞名│捨棄│排除│連結│掛載異常。

exit：有衝突／撞名／路由錯誤時 1（可作 CI 守門）。

檢查不通過時

2. 確認本機改動（每次必查）

  • manifest 可讀：發現本機改動或 untracked 檔案就列出並問「捨棄並重建？」。
  • 產物目錄存在但 manifest 壞掉／被刪：無從得知內容，一律先問。
  • 產物目錄不存在：第一次建置，直接進行。

3. 建置 → 掛載

唯讀agsy status

三方比對（來源 ↔ manifest ↔ 產物/掛載），報告結構：

① sources → 產物（apply 的方向）

  • behind：來源更新了還沒重建。特別標註「來源檔已刪除 ⚠（apply 後項目消失）」與「來源路徑整個不見 ⚠（先修路徑，別急著 apply）」。
  • new：來源有新檔案還沒進產物。
  • missing artifacts：產物複本被刪（工具透過連結讀不到；apply 可重建）。

② 產物 → sources（promote 的方向）

  • local changes：產物被改、可寫回。可能附加：⚠ 來源也改了（需人工比對）／⚠ 多 bucket 複本改成不同內容／⚠ 來源檔已刪（promote 會重建）／⚠ 來源根目錄不見（promote 拒絕）。
  • untracked：產物端新增、manifest 不認識——promote 寫不回、apply 會刪；要保留請搬進來源再 apply。

③ mounts ＋ ④ 摘要

各連結狀態（正常／不見／指錯斷掉／被佔用／孤兒），最後一行統計＋下一步建議（如「先 promote 保住改動，再 apply」）。

exit code：0＝同步、1＝有落差（適合 CI / git hook；非 TTY 只印報告）。互動終端且有落差時，結尾出現行動選單可直接跳 promote / apply。

agsy promote skills/code-review       # 單一項目（類別/名稱）

agsy promote --all                    # 全部寫回原始來源（先列清單再確認）

  • 多 bucket 複本同步為相同內容。
  • 更新 manifest 基準：這筆改動回到無落差，status 不再列出；下一步執行 apply 完成重建。
  • --to 改道會提醒：舊來源的檔案還在，下次建置會收到新舊兩份同名——確認後手動刪舊的。

C-3. 適配器（Adapters）

適配器是什麼？

內建的「各家工具掛載範本」：記錄工具的設定目錄、rules / skills / workflows 該連到哪個名字、以及專屬 bucket。只在 init 時發揮作用——你勾選工具，init 就把對應 mount 段落與 bucket 寫進 agsy.yaml；執行期 plan / apply / status 只看 agsy.yaml，所以 init 之後可任意手改，不受範本限制。

內建適配器一覽

只想快速查「哪個類別掛在哪個資料夾」，看核心概念的總表一張就夠；下面是逐工具的細節。

Claude Code（bucket: claude，目錄 .claude/）

連結指向產物用途
.claude/rulesrules規則檔
.claude/skillsskillsAgent Skills
.claude/commandsworkflows/claude斜線指令——標 target: claude 的 workflow 在 Claude Code 中就是 /<檔名>

OpenAI Codex（bucket: codex，目錄 .codex/）

連結指向產物用途
.codex/promptsworkflows/codex自訂 prompts

只掛 workflows（遵循 Codex CLI custom prompts 慣例；原始碼註記專案層級支援仍待實測）。因此只勾 Codex 時 init 會警告：rules 和 skills 會建置但沒工具讀——需要可自行補 links。

Antigravity（bucket: agents，目錄 .agents/）

連結指向產物
.agents/rulesrules
.agents/skillsskills
.agents/workflowsworkflows/agents

bucket 與適配器的關係

每個適配器宣告一個 bucket。init 時 route.buckets＝勾選的適配器 bucket 聯集（＋手動加過的、＋自訂 mount 用到的）。workflow 以 target: 指名去哪些工具；沒標的依 route.default。

自訂掛載（接入不在清單的工具）

任何「從固定目錄讀 Markdown」的工具都能手動接上：

build:
  route:
    buckets: [claude, codex, mytool]   # 要有專屬 bucket 記得加
    default: [claude, codex, mytool]

mount:
  - dir: .mytool
    links:
      rules:   rules                # 共用 rules
      prompts: workflows/mytool     # 專屬 workflow bucket

規則回顧：目標第一層是某類別的 to；只有 workflows 可加第二層 bucket（須在 buckets 裡）；dir 不可重複、不可在產物或來源目錄內。自訂項目不會被 init 洗掉——之後再跑 init 編輯，自訂 mount 與 bucket 都原樣保留。

（進階）為 agsy 專案新增內建適配器

給想貢獻上游的人：內建適配器是 repo 內 adapters/ 下的 YAML，經 go:embed 打包。新增工具只要放一個 <name>.yaml：

# adapters/mytool.yaml
name: mytool          # 內部識別名
display: My Tool      # init 選單顯示名
bucket: mytool        # 專屬 workflow bucket
mount:
  dir: .mytool
  links:
    rules:   rules
    prompts: workflows/mytool

重新編譯後，init 的工具多選清單就會出現它。

C-4. 情境全覽：apply 與 promote 的每一種狀況

apply 和 promote 遇到「兩端不一致」時到底會做什麼、什麼時候會被防呆擋下——這一章把所有情境列成對照表。遇到不確定的狀況，先跑 agsy status（唯讀），再拿它的輸出對照本章。

C-4-1. 判斷的基準：manifest 怎麼知道「誰改了」

每次 apply 建置時，manifest（.agsy/.agsy-manifest.json）會為每個項目記下兩個指紋：

                    ┌── SrcHash：建置當下「來源檔」的內容指紋
 建置當下拍快照 ──────┤
                    └── Hash   ：建置當下「產物複本」的內容指紋

 之後任何時刻：
   現在的來源檔  vs  SrcHash   不同 → 來源端改了（behind，該 apply）
   現在的產物檔  vs  Hash      不同 → 產物端改了（local changes，該 promote）
   兩個都不同              → 兩端都改了（要人工處理）

因為有「建置當下」這個第三方基準，agsy 能分辨「誰改的」，而不是只看到「兩邊不一樣」。

C-4-2. 主對照表：來源端 × 產物端

「產物端」＝ .agsy/ 裡的複本；你或 AI 工具透過 .claude/ 等掛載連結碰到的就是這一份檔案（名詞定義見核心概念）。

#來源端產物端status 顯示apply 的行為promote 的行為
1沒變沒變（無落差）重建，內容不變無事可做
2內容改了沒變behind✅ 重建，同步新內容沒有改動可寫回
3沒變內容改了local changes⚠ 先列清單，問「捨棄並重建？」✅ 寫回來源
4內容改了內容改了local changes＋⚠ 來源也改了⚠ 問「捨棄並重建？」（產物端改動會消失）✘ 拒絕——直接覆蓋會清掉來源的新內容，請人工合併（見 C-4-3）
5新增檔案—new✅ 收進產物與它無關
6—新增檔案untracked⚠ 列出並確認後刪除（重建=以來源為準）✘ 寫不回——它沒有對應的來源位置（見 C-4-4）
7檔案被刪沒變behind＋⚠ 來源已刪項目從產物消失（status 事先就警告過）沒有改動可寫回
8檔案被刪內容改了local changes＋⚠ 來源檔已刪⚠ 問「捨棄？」，同意後項目消失⚠ 明確問「要重建來源檔嗎？」，答應才寫
9整個來源路徑不見（沒 clone／碟未掛載／打錯字）任何狀態⚠ 來源路徑不見（與「檔案被刪」明確區分）✘ 整個拒絕執行——不從殘缺的來源清單重建，否則缺席來源的項目會被清光✘ 拒絕該來源的項目——先修好路徑
10沒變產物複本被刪missing artifacts✅ 重建補回沒有內容可寫回（不算 local change）
11—多個 bucket 複本，改成「不同」內容local changes＋⚠ 多複本分歧⚠ 問「捨棄？」✘ 拒絕——哪份是對的要由人決定
12—多個 bucket 複本，改成「相同」內容local changes（算一項）⚠ 問「捨棄？」✅ 寫回，並把所有複本同步成一致

三條通用規律，記住就不用背表：

  1. apply 永遠以來源為準——重建就是「把產物變成來源現在的樣子」，所以產物端任何未寫回的東西都會被蓋掉／刪掉，但一定先列清單問你（第 3、4、6、8、11、12 列）。
  2. promote 只在「能安全寫回」時動手——凡是會蓋掉來源新內容（4）、無處可寫（6、10）、或需要人做選擇（11）的情境，一律拒絕或改問你。
  3. 「路徑不見」和「檔案被刪」是兩回事（9 vs 7）——前者多半是環境問題（repo 沒 clone、外接碟沒掛），agsy 直接停下要你先修，絕不會當成「你刪了檔案」處理。

C-4-3. 情境 4 手把手：兩端都改了怎麼辦

  1. agsy status 找到那個項目，記下它的原始來源路徑（報告裡有印）。
  2. 手動比對兩份：來源檔（如 ~/all-ai-lib/rules/x.md）vs 產物檔（如 .agsy/rules/x.md，從 .claude/rules/x.md 點進去的也是同一份）。
  3. 把要保留的內容合併進來源檔（記住：來源是唯一真相）。
  4. agsy apply 重建——基準重設，回到情境 1。

C-4-4. 情境 6 手把手：想保留 untracked 檔案

untracked 通常是 AI 工具透過工具目錄在產物端直接新建的檔案（例如它幫你寫了一個新 rule）。想留下來：

# 把檔案從產物搬進某個來源的對應子目錄
mv .agsy/rules/new-rule.md ~/all-ai-lib/rules/
agsy apply     # 之後它就是正式項目，開始被追蹤

不搬就 apply 的話，會在確認清單裡看到它，同意後被刪除。

C-4-5. 掛載連結的情境

掛載連結本身也可能出狀況——這不屬於兩端的內容差異，是「通道」本身的問題：

情境status 顯示怎麼發生處理
連結不存在✘ 連結不見手動刪了、或還沒 apply 過agsy apply 重建
連結指錯地方✘ 指向…非目前設定的目標改過 build.out、或連結被動過agsy apply 重建

這些檢查刻意排在「確認捨棄改動」之前——不能讓你先同意丟掉改動、等建置跑完才發現這輪注定失敗：

狀況訊息重點處理
任一來源路徑不存在拒絕從殘缺清單重建修好路徑（clone／掛載／改錯字）
掛載點被真實目錄佔用拒絕並列出，絕不代刪手動搬走或刪除
workflow 路由錯誤（target 指到不存在的 bucket）列出待修檔案修 front-matter 或補 route.buckets

最終輸出名撞名（collision）列出撞名組改名（rename 後仍可能巧合撞名，一律擋下不互蓋）

manifest 版本比 agsy 新用舊規則解讀新格式太危險升級 agsy（或刪掉 .agsy/ 重建）

C-4-7. promote 的完整防呆清單

除了主表的內容判斷，promote 對「寫到哪裡」還有一整組安全檢查：

防呆規則
寫回位置鎖定只能寫進該項目自己的格子：<設定的來源>/<類別子目錄>/<原始名稱>——manifest 被竄改也無法把寫入導去別處
--to 白名單只能指向 agsy.yaml 裡已設定的來源；寫到別處＝脫離管理，直接拒絕
拒寫符號連結寫回目標若是 symlink，拒絕（不穿透連結寫檔）
專案外要多確認目標在專案外（共用庫）時多問一次——會影響所有用到該庫的專案
--all --to 不支援整批改道會讓來源與 manifest 脫鉤
改名 skill 還原名稱寫回時自動把 SKILL.md 的 name 還原成原始名稱（-fromlib-… 只屬於產物）
--to 改道提醒舊來源那份還在，下次建置會出現新舊兩份同名——確認後手動刪舊的
寫回後更新基準產物指紋與來源指紋同步刷新：這筆改動回到無落差，也不會誤判「來源也改了」；下一步執行 apply 完成重建

D-1. 觀念與日常使用

Q1：我直接改了 .claude/rules/ 裡的檔案，下次 apply 會不會被蓋掉？

.claude/rules 是指向 .agsy/rules 的連結，你改的是產物。apply 重建前會偵測到「本機改動」，先列清單問你要不要捨棄，不會不吭聲蓋掉。想保留：先 agsy promote 寫回來源，再 apply。

Q2：.agsy/ 要不要進版控？agsy.yaml 呢？

.agsy/ 不要（可重建產物，init 會主動幫你加 .gitignore）；agsy.yaml 要（專案同步設定，也是 init 編輯模式取代註解時的後悔藥）。

Q3：改了來源檔，工具什麼時候看到新內容？

跑完 agsy apply 之後。agsy 不是常駐程式、不自動監看——可配 git hook（agsy status exit 非 0 就提醒）。

Q4：plan、status、doctor 差在哪？

doctor＝環境健檢；plan＝這次建置的完整預演；status＝現況與基準的落差。三個都唯讀，隨便跑都安全。

Q5：可以在子目錄執行嗎？

可以，除 init 外都會往上層找 agsy.yaml。init 刻意只看目前目錄，避免誤改上層專案的設定。

Q6：多個專案共用一個來源庫？

可以，正是設計初衷。各專案的 sources 指向同一個 ~/all-ai-lib 即可。對共用庫 promote 寫回時會多一道確認（影響所有用到它的專案）。

D-2. 我的檔案怎麼了

Q7：為什麼我的 skill 沒被收進去？

skill 必須是目錄＋內含 SKILL.md；目錄內不能有符號連結；名稱不能 . 開頭。doctor / plan 會直接告訴你原因。

Q8：rules 目錄裡某檔案沒被收？

rules / workflows 只收單一 .md：目錄、非 .md、. 開頭、符號連結都不收；原因列在 plan 的排除清單。

Q9：status 說有 untracked，apply 還會刪掉它？

untracked＝產物端新增、manifest 不認識的檔案，沒有來源位置所以 promote 寫不回、apply 會刪。要保留：搬進某個來源的對應子目錄，再 apply。

Q10：檔名多了 -fromlib-xxx？

同名衝突 rename 策略附加的來源標籤：兩份都保留、看檔名知道來自哪個來源。skill 改名時 front-matter 的 name 也同步改寫（promote 時自動還原）。

Q11：workflow 沒出現在任何工具裡？

三種可能（plan 都會標）：target 指到不存在的 bucket（路由錯誤，apply 拒絕）；沒標 target 且 route.default 為空（不放，有警告）；標的 bucket 沒有任何 mount 連結去讀。

Q12：不小心刪了 .agsy/ 裡的東西？

沒事，產物本來就可重建：agsy apply 一次全部回來。manifest 壞掉時 apply 會多問一次確認再重建。

D-3. 衝突與寫回

Q13：兩個來源同名檔案會怎樣？

由該類別 on_conflict 決定：rename 兩份都留（附標籤）；error 停下列清單；first 只留優先權高的。init 必答題，無隱含預設。

Q14：為什麼 skills 建議 error？

skill 靠描述語意觸發，同名並存時工具選哪個難預測；rename 還需改寫 SKILL.md 的 name。同名 skill 通常該整併，建議人工處理。

Q15：「來源也改了」promote 拒絕寫回？

保護機制：直接覆蓋會清掉來源新內容。手動比對兩份、把要留的合併進來源，然後 apply 重建，基準重設後恢復正常。

Q16：想把項目從共用庫搬到專案庫？

agsy promote skills/code-review --to ./repo-ai-lib

promote 完會提醒：舊來源那份還在，下次建置會收到兩份同名——確認新位置沒問題後手動刪舊的。

Q17：--all 和逐一寫回的差別？

--all 先按來源分組列出全部（寫到共用庫的特別標警告），確認一次後逐項寫回；單項失敗不中止整批，最後列失敗清單。--all 不能配 --to。

D-4. 平台與環境

Q18：Windows 需要管理員權限或開發人員模式嗎？

不需要。agsy 用 junction，一般帳號即可建立。唯一注意：junction 存絕對路徑，搬移專案後要重跑 agsy apply（macOS / Linux 用相對 symlink，不受影響）。

Q19：換電腦／共用庫還沒 clone，status 一堆警告？

status 會明確區分「來源路徑不見」（repo 沒 clone、外接碟沒掛、路徑打錯）和「來源檔被刪」。此時 apply 也會拒絕重建，避免把缺席來源的項目清掉。補齊路徑再操作即可。

Q20：可以在 CI / git hook 用嗎？

可以：status exit 0/1 當檢查；動作類指令加 --yes；沒有 --yes 時非互動確認一律取消，不會意外破壞。agsy init --yes <sources...> 可非互動初始化。

Q21：介面語言怎麼切？

export AGSY_LANG=zh-TW＝繁中；AGSY_LANG=en＝英文；沒設時看 LC_ALL / LANG。

Q22：如何完全移除 agsy？

各專案 agsy clean → 不需要的話刪 agsy.yaml → 刪執行檔，依當初的安裝方式：brew uninstall agsy／winget uninstall IngSquared99.agsy／Go 安裝的刪 ~/go/bin/agsy。

Q23：「孤兒連結」是什麼？

以前 apply 建過、後來你從 mount 設定拿掉的連結；工具還在透過它讀舊內容。apply 只回報不刪；手動刪或 agsy clean 一併清。

Q24：掛載點已有真實的 .claude/skills 目錄？

agsy 絕不刪非它建立的真實檔案。把既有內容搬進某個來源（讓它被 agsy 管理），或自行備份後刪除，再 apply。

Q25：來源裡的符號連結會不會把外部檔案（如私鑰）帶出去？

不會。掃描時符號連結一律不收（含 skill 內部——含連結的 skill 整個略過），複製階段還有第二道防線直接拒絕。產物會被掛載給各工具讀，這是刻意的安全設計。
