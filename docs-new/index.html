0. 核心概念：agsy 是什麼？

它解決的問題

當你同時使用多個 AI 開發工具（Claude Code、OpenAI Codex、Antigravity…），每個工具都有自己的指令檔目錄：Claude Code 讀 .claude/rules/、.claude/skills/、.claude/commands/；Codex 讀 .codex/prompts/；Antigravity 讀 .agents/。同一份規範得複製好幾份、改一處要同步好幾處，而且你可能還想把「個人共用的一套」和「專案專屬的一套」疊在一起用。

agsy（agent-sync）：把多個來源（sources）的指令檔合併建置成單一產物目錄（預設 .agsy/），再用目錄連結掛載進每個工具的讀取位置。改動時只改來源，跑一次 agsy apply，所有工具同時更新。

三層架構

┌────────────────────┐
│  來源 sources       │  ~/all-ai-lib/       （個人共用庫，跨專案）
│ （你維護的原始檔）    │  ./repo-ai-lib/      （專案內的庫）
└─────────┬──────────┘
          │  agsy apply（掃描 → 合併 → 複製）
          ▼
┌────────────────────┐
│  產物 build.out     │  .agsy/rules/
│ （可整個重建的成品）  │  .agsy/skills/
│                    │  .agsy/workflows/<bucket>/
└─────────┬──────────┘
          │  agsy apply（建立目錄連結 symlink / junction）
          ▼
┌────────────────────┐
│  掛載 mount         │  .claude/rules  → ../.agsy/rules
│ （各 AI 工具實際     │  .claude/skills → ../.agsy/skills
│   讀取的位置）       │  .codex/prompts → ../.agsy/workflows/codex
└────────────────────┘
  • 來源：你真正維護、進版控的原始檔。可有多個，順序＝優先權。
  • 產物（build.out，預設 .agsy/）：整個目錄視為可重建的拋棄式產出——apply 每次清空重建，手寫的東西別直接放進去（除非打算用 promote 寫回）。
  • 掛載：在各工具目錄建立指向產物的連結；工具看到的是連結，內容都在 .agsy/。

三種類別（categories）

類別來源子目錄（預設）格式輸出位置
rulesrule/單一 .md 檔.agsy/rules/
skillsskill/目錄，內含 SKILL.md.agsy/skills/
workflowsworkflow/單一 .md，front-matter 可標 target.agsy/workflows/<bucket>/

workflows 的分流（routing 與 bucket）

rules 和 skills 所有工具共用一份；workflows 則依 front-matter 的 target 欄位分流到不同 bucket（子目錄）：

---
target: claude          # 只給 Claude Code
# 或 target: [claude, codex]
---
Release 流程說明…

沒標 target 的 workflow 落入 route.default 設定的 bucket（建議設為全部）。

雙向資料流：apply 與 promote

sources  ──── apply ───▶  .agsy/（掛載給工具）
sources  ◀── promote ───  .agsy/
  • apply（正向）：來源改了 → 重建產物、更新掛載。
  • promote（反向）：你（或 AI 工具）直接改了掛載側的檔案 → 寫回來源，改動才不會在下次 apply 被蓋掉。

agsy 用 .agsy/.agsy-manifest.json 記錄建置當下來源與產物的雜湊值，status 因此能精準區分「來源更新了還沒重建」（behind）、「掛載側被改了還沒寫回」（local changes）、以及兩邊同時被改（需人工合併）。

設計上的安全底線

  1. 不碰真實檔案：掛載點若已被「真實目錄／檔案」佔用，一律報錯請你手動處理，絕不代為刪除。
  2. 同名策略必須明說：on_conflict 每類別必填，沒有隱含預設。
  3. 刪除前必先確認：偵測到未寫回的改動一定先問；非互動環境沒有 --yes 就取消。
  4. 產物目錄防呆：build.out 只能是專案內專用目錄，指到家目錄／來源／專案根都會被擋。
  5. 不收符號連結：避免透過連結把來源以外的檔案夾帶進產物。

名詞小抄

名詞意思
source（來源）你維護的原始指令檔庫（sources 陣列）
build out（產物）apply 建置出的目錄，預設 .agsy/，整個可重建
mount（掛載）在工具目錄建立指向產物的連結
bucketworkflows 分流的目的地子目錄（如 claude、codex）
manifest.agsy/.agsy-manifest.json，建置紀錄與變更偵測基準
source tag同名改名時附加的來源識別，如 -fromlib-all-ai-lib
adapter（適配器）內建工具掛載範本，init 用來產生 mount 設定
behind來源已更新、產物還沒重建（該 apply）
local changes掛載側被改了、還沒寫回（該 promote）
untracked掛載側新增、manifest 不認識的檔案（apply 會刪；要留請搬回來源）
orphan（孤兒連結）之前 apply 建立、現在設定已不引用的連結

A. 安裝說明

agsy 是單一執行檔（Go 編譯），無其他相依。支援 macOS（Intel / Apple Silicon）、Linux（x64 / arm64）、Windows（x64 / arm64）。

A-1. macOS / Linux：一行安裝（建議）

curl -fsSL https://raw.githubusercontent.com/IngSquared99/agent-sync/main/install.sh | sh

腳本會：偵測平台 → 從 GitHub Releases 下載對應壓縮檔與 checksums.txt → 驗證 SHA-256 → 安裝到 /usr/local/bin（不可寫時透過 sudo，可能要求密碼）。

環境變數作用
AGSY_INSTALL_DIR改變安裝目錄（預設 /usr/local/bin）
AGSY_DRYRUN=1只印出會做什麼，不實際下載安裝

A-2. Windows：PowerShell 一行安裝

irm https://raw.githubusercontent.com/IngSquared99/agent-sync/main/install.ps1 | iex

安裝到 %LOCALAPPDATA%\Programs\agsy 並加入使用者層級 PATH，不需系統管理員權限，一樣驗證檢查碼。安裝完請開新終端機視窗再執行 agsy version。

A-3. 手動下載

到 https://github.com/IngSquared99/agent-sync/releases/latest 下載：

平台檔名
macOS Apple Siliconagsy_mac_apple_silicon.tar.gz
macOS Intelagsy_mac_intel.tar.gz
Linux x64 / arm64agsy_linux_x64.tar.gz / agsy_linux_arm64.tar.gz
Windows x64 / arm64agsy_windows_x64.zip / agsy_windows_arm64.zip

解壓後把 agsy（Windows 為 agsy.exe）放進 PATH 內的目錄。

A-4. 從原始碼建置

git clone https://github.com/IngSquared99/agent-sync.git
cd agent-sync
go build -o agsy ./cmd/agsy
# 或
go install github.com/IngSquared99/agent-sync/cmd/agsy@latest

自建版本 agsy version 顯示 dev（版號由 release 流程注入），功能不受影響。需要 Go 1.22+。

A-5. 驗證安裝

agsy version   # agsy v1.2.3 (commit …, built …, go1.22.x, darwin/arm64)
agsy doctor    # 唯讀環境健檢

A-6. 介面語言

判斷順序：AGSY_LANG → LC_ALL → LANG；值以 zh 開頭用繁體中文，其餘英文。強制中文：export AGSY_LANG=zh-TW。

A-7. 升級 / A-8. 移除

升級：重跑安裝指令（永遠抓最新 release，直接覆蓋）。移除：各專案先 agsy clean，再刪執行檔（macOS/Linux：sudo rm /usr/local/bin/agsy；Windows：刪 %LOCALAPPDATA%\Programs\agsy 並清 PATH）。

B. 快速上手：Command Line 指引

B-1. 兩種操作方式

agsy            # 不帶參數：互動選單（顯示狀態摘要；適合新手）
agsy <指令>      # 直接執行（適合熟手與腳本）

第一次執行且還沒有設定檔時，選單會直接引導你進 init。

B-2. 指令速查表

指令做什麼寫入？
agsy init [sources...]問答式產生 agsy.yaml（已存在則編輯模式）寫 agsy.yaml
agsy doctor環境健檢唯讀
agsy plan完整預覽 build + mount唯讀
agsy apply檢查 → 確認 → 清空重建 → 掛載寫 .agsy/ 與連結
agsy status三方比對報告落差唯讀
agsy promote掛載側改動寫回來源寫來源
agsy clean移除連結與產物（保留 agsy.yaml）刪除產物
agsy version / help版本 / 說明唯讀

全域旗標 --yes（-y）：所有確認一律「是」，給 CI／腳本用。沒有它時，非互動環境需要確認的動作會直接取消，絕不硬做。

B-3. Step 0：準備來源目錄

mkdir -p ~/all-ai-lib/rule ~/all-ai-lib/skill ~/all-ai-lib/workflow
mkdir -p ./repo-ai-lib/rule ./repo-ai-lib/skill ./repo-ai-lib/workflow

格式要求（不合規的檔案會被略過並回報原因）：rule/ 單一 .md；skill/ 目錄＋SKILL.md、內部不可含符號連結；workflow/ 單一 .md，front-matter 可標 target:。

B-4. Step 1：agsy init

在專案根目錄執行。問答依序：來源路徑（依優先權）→ 掛載哪些工具（多選）→ 三個類別的同名策略（必答；建議 rules=rename、skills=error、workflows=rename）→ 產物目錄（預設 .agsy）→ 無 target 的 workflow 去向。完成後詢問是否把產物目錄加入 .gitignore（建議加；agsy.yaml 則應進版控）。

非互動環境：agsy init --yes ~/all-ai-lib ./repo-ai-lib——來源用參數給，--yes＝同意建議預設策略。

B-5. Step 2：agsy plan（預覽）

把 apply 會做的每件事演練一遍但完全不寫入：來源狀態與標籤、各類別收錄清單、改名與分流、被略過的檔案與原因、衝突、每個連結將採取的動作。看到「未寫入任何檔案」再進下一步。

B-6. Step 3：agsy apply（建置與掛載）

agsy apply
# ✔ build done: 12 items → .agsy/
# ✔ mount done: 5 links

之後打開 .claude/ 就能看到指向 .agsy/ 的連結，工具可直接讀取。

B-7. 日常循環

改了來源檔       → agsy apply
不確定狀態       → agsy status
掛載側被改了     → agsy promote → agsy apply
暫時移除全部產出  → agsy clean

心智模型只有一條：來源是唯一的真相來源。正常改動改來源＋apply；改到掛載側就用 promote 收回來。

B-8. CI / git hook

# pre-commit：不同步就擋下
agsy status || { echo "agsy 不同步，請先 agsy apply"; exit 1; }
# CI 重建
agsy apply --yes

C-1. 個人設定檔：agsy.yaml

放在專案根目錄、建議進版控。通常由 agsy init 產生；以下逐欄說明，讓你能放心手改。

完整範例

# 路徑語法：~ 開頭＝家目錄；相對路徑＝以本檔所在目錄為基準；絕對路徑＝原樣
version: 1

sources:                      # 有序陣列，越前面優先權越高
  - ~/all-ai-lib
  - ./repo-ai-lib

build:
  out: .agsy                  # 必須在專案內（apply 會整個清空重建）

  categories:                 # 來源子目錄 → 產物子目錄（三個 to 不可相同）
    rules:     { from: rule, to: rules }
    skills:    { from: skill, to: skills }
    workflows: { from: workflow, to: workflows }

  on_conflict:                # 同名處理：first / rename / error（每類別必填）
    rules:     rename
    skills:    error
    workflows: rename

  route:                      # workflow 分流
    field: target
    default: [claude, codex]
    buckets: [claude, codex]

mount:
  - dir: .claude              # Claude Code
    links:
      rules:    rules
      skills:   skills
      commands: workflows/claude
  - dir: .codex               # OpenAI Codex
    links:
      prompts:  workflows/codex

路徑語法（全檔通用）

寫法解讀適合
~/xxx家目錄展開跨專案共用庫
./xxx以 agsy.yaml 所在目錄為基準（不是執行目錄）專案內的庫
/abs/path原樣使用特殊佈局

因此從專案子目錄執行也正常——agsy 像 git 一樣往上找設定檔（唯一例外：init 只看目前目錄）。

version

設定格式版本，目前 1；省略視為 1。檔案版本高於 agsy 支援上限時會被要求升級 agsy。

sources（必填，至少一個）

  • 順序＝優先權：first 策略保留排前面的來源。
  • 來源缺某類別子目錄是正常的；整個路徑不存在時 plan 仍可預覽（標明不完整），但 apply 拒絕執行。
  • 來源標籤：取路徑最後一段去掉開頭的點（~/all-ai-lib → all-ai-lib）；撞名時自動併入父目錄名、仍相同才加數字，保證唯一。

build.out（產物目錄）

預設 .agsy。apply 會整個清空、clean 會整個刪除，所以有嚴格防呆——指向專案根／上層、專案外、家目錄、與來源互相包含的設定都會直接被擋。一句話：只能是專案內的專用子目錄。

build.categories

from＝來源掃描子目錄、to＝產物輸出子目錄；只寫一半另一半補預設；三個 to 必須互不相同。

收錄規則（不合規會被略過並回報，不會默默消失）

規則說明
. 開頭一律略過（隱藏檔不回報，避免 .DS_Store 洗版）
符號連結一律不收——建置複製「內容」，連結可能夾帶來源外的檔案（如私鑰）進被掛載的產物
rules / workflows只收單一 .md；目錄不收
skills只收目錄且必須含 SKILL.md；內部含任何符號連結則整個不收

build.on_conflict（每類別必填）

策略行為適合
rename兩份都留，檔名附來源標籤：python-style-fromlib-all-ai-lib.mdrules（全域基底＋專案補充常需並存）
error停止並列出衝突，人工處理（最保守）skills（見下）
first只留優先權最高的那份，其餘捨棄（plan 會列出）確定「專案覆蓋全域」時

為什麼 skills 建議 error？skill 靠描述語意觸發，同名並存時工具選哪個難預測；且 skill 名稱受 Agent Skills 規範限制（小寫 a-z0-9、單一連字號、與目錄同名），rename 還得改寫 front-matter 的 name（agsy 會自動做、promote 時自動還原）。同名 skill 通常代表該整併，所以預設請人工處理。

撞名（collision）：rename 後或名稱巧合使最終輸出名相同（如 God-Lib 與 god-lib 淨化後相同）時，一律擋下建置，不默默互蓋。

build.route（workflow 分流）

  • field：讀哪個 front-matter 欄位（預設 target）。
  • workflow 寫 target: claude 或 target: [claude, codex]，建置時複製到對應 workflows/<bucket>/。
  • 指到 buckets 沒有的值＝路由錯誤：plan 全列、apply 拒絕。
  • 沒標 target → 套 default；default: [] 則不放進任何 bucket 並警告。建議 default 涵蓋全部 bucket。

mount（必填，至少一個）

  • dir＝放連結的目錄；links＝連結名稱: 產物內相對目標。
  • 目標第一層必須是某類別的 to；只有 workflows 可有第二層 bucket（且須在 route.buckets 裡）；不能更深。
  • 也會擋：同一 dir 重複、dir 在產物目錄或來源目錄內。
  • 連結實作：macOS/Linux 用相對 symlink（專案搬移仍有效）；Windows 用 junction（免特權，但存絕對路徑——搬移專案後要重跑 apply）。

驗證錯誤速查

設定載入時所有問題一次列出。常見訊息（意譯）與處理：

錯誤處理
sources 未設定至少填一個來源
on_conflict.某類別 未設定三類別都明確填 first / rename / error
build.out 會清掉…（危險路徑）改回專案內專用目錄（如 .agsy）
兩個類別的 to 相同改成不同子目錄
links 指到不存在的頂層目標第一層要是 rules/skills/workflows（依 to 設定）
links 指到不在 buckets 的 bucket把該 bucket 加進 route.buckets 或改目標
version 超過支援上限升級 agsy

C-2. 指令說明

總覽

agsy                        互動選單（含狀態摘要）
agsy init [sources...]      產生 / 編輯 agsy.yaml
agsy doctor                 環境健檢（唯讀）
agsy plan                   預覽 build + mount（唯讀）
agsy apply                  檢查 → 確認 → 清空重建 → 掛載
agsy status                 三方比對（唯讀；exit 0=同步 1=有落差）
agsy promote [item] [--to <source>] [--all]   寫回改動
agsy clean                  移除連結與產物（反安裝）
agsy version / help         版本 / 說明

通用行為：除 init 外都會往上層尋找 agsy.yaml；語言依 AGSY_LANG/LC_ALL/LANG 切換；Windows 雙擊執行時結束前會暫停。全域旗標 --yes/-y＝所有確認視為「是」。

建議節奏：第一次 init → doctor → plan → apply；改了來源 apply；改了掛載側 status → promote → apply；不確定 status；移除 clean。

互動agsy（互動選單）

找不到設定檔時直接引導進 init。有設定檔時，頂部顯示一行狀態摘要（behind / new / local changes / untracked / missing outputs / mount issues 數量），再列出所有功能選項；偵測到本機改動時 apply 選項旁會標註「需要先確認」。

agsy init [sources...]

全新建立

依序詢問：來源路徑 → 掛載哪些工具（多選，來自內建適配器）→ 三類別同名策略（必答）→ 產物目錄 → 無 target 的 workflow 去向。寫檔後：若有類別「會建置但沒工具掛載」會警告（例如只勾 Codex 時 rules/skills 沒人讀）；並詢問是否把產物目錄加進 .gitignore。

編輯模式（設定檔已存在）

  • 每題預帶目前值，按 Enter 保留原值；已掛載的工具預先勾選。
  • 手動加過的不會被洗掉：自訂 mount、手加的 bucket、改過的 categories 與 route.field 都原樣保留。
  • 寫入前顯示逐行 diff 並確認；沒變更就直接結束。
  • 注意：yaml 註解會被範本註解取代——自訂註解要事後補回（設定檔進版控就是為了這種時刻）。

非互動環境

agsy init --yes ~/all-ai-lib ./repo-ai-lib

init 的核心是「策略必須由使用者明確選擇」，所以沒人能回答時預設取消；--yes＝明確同意建議預設（rules=rename、skills=error、workflows=rename），來源用參數傳。

唯讀agsy doctor

環境健檢，不做任何動作：

  1. 設定檔找得到、格式合法。
  2. 來源路徑存在與否（不存在＝✘）。
  3. 各來源各類別子目錄：缺目錄只是 ⚠；存在則統計會收錄的檔數——計數規則與 build 完全相同，並逐一列出被略過的檔案與原因。
  4. 各掛載點現況（可建立／已是連結／指錯或斷掉／被真實目錄佔用）。
  5. 連結能力實測：實際建一個暫時連結再刪掉（Windows 驗證 junction 可用、免特權）。

結尾統計 N errors, M warnings；有錯誤時 exit 1。適用：裝完驗證環境、「檔案為什麼沒被收」、換機後檢查。

唯讀agsy plan

把 apply 完整演練一遍、保證不寫入。輸出三段：

  • build 預覽：來源清單（優先權、存在狀態、標籤）；各類別收錄項目、誰被改名、workflow 分到哪些 bucket 及原因；被 first 捨棄的、被排除的（附原因）；擋路問題（同名衝突、最終名撞名、路由錯誤）一次全列。
  • mount 預覽：每個連結將建立／刪除重建／修復／或被真實目錄擋住（apply 會失敗）。
  • 摘要：項目數│改名│衝突│撞名│捨棄│排除│連結│掛載異常。

exit：有衝突／撞名／路由錯誤時 1（可作 CI 守門）。

agsy apply

1. 前置檢查（全過才會進入確認）

檢查不通過時
所有來源存在✘ 拒絕：不從殘缺來源清單重建（否則缺席來源的項目會被清掉）
掛載點未被真實目錄佔用✘ 拒絕並列出，請手動搬走（絕不刪非 agsy 建的東西）
無路由錯誤／同名衝突／撞名✘ 拒絕；plan 可看完整清單

檢查刻意放在「確認捨棄改動」之前：不能讓你先同意丟掉改動、等建置跑完才發現這輪注定失敗。

2. 確認本機改動（每次必查）

  • manifest 可讀：發現本機改動或 untracked 檔案就列出並問「捨棄並重建？」。
  • 產物目錄存在但 manifest 壞掉／被刪：無從得知內容，一律先問。
  • 產物目錄不存在：第一次建置，直接進行。

3. 建置 → 掛載

清空產物 → 複製（改名的 skill 同步改寫 SKILL.md 的 name）→ 確保所有連結目標目錄存在（沒 workflow 也會建立空的 workflows/<bucket>/，連結才不會斷）→ 寫 manifest → 建連結。掛載失敗時建置成果完好，修好問題重跑 apply 即可。

4. 孤兒連結回報

之前 apply 建過、現在設定不再引用的連結會列出提醒——只回報不刪除；手動刪或 agsy clean。

唯讀agsy status

三方比對（來源 ↔ manifest ↔ 產物/掛載），報告結構：

① sources → 產物（apply 的方向）

  • behind：來源更新了還沒重建。特別標註「來源檔已刪除 ⚠（apply 後項目消失）」與「來源路徑整個不見 ⚠（先修路徑，別急著 apply）」。
  • new：來源有新檔案還沒進產物。
  • missing artifacts：產物複本被刪（掛載側讀不到；apply 可重建）。

② 產物 → sources（promote 的方向）

  • local changes：產物被改、可寫回。可能附加：⚠ 來源也改了（需人工比對）／⚠ 多 bucket 複本改成不同內容／⚠ 來源檔已刪（promote 會重建）／⚠ 來源根目錄不見（promote 拒絕）。
  • untracked：掛載側新增、manifest 不認識——promote 寫不回、apply 會刪；要保留請搬進來源再 apply。

③ mounts ＋ ④ 摘要

各連結狀態（正常／不見／指錯斷掉／被佔用／孤兒），最後一行統計＋下一步建議（如「先 promote 保住改動，再 apply」）。

exit code：0＝同步、1＝有落差（適合 CI / git hook；非 TTY 只印報告）。互動終端且有落差時，結尾出現行動選單可直接跳 promote / apply。

agsy promote

agsy promote                          # 互動多選，每項可改寫回目標
agsy promote skills/code-review       # 單一項目（類別/名稱）
agsy promote code-review              # 只給名稱；跨類別撞名時列出全名請重下
agsy promote skills/code-review --to ./repo-ai-lib   # 改寫回到指定來源
agsy promote --all                    # 全部寫回原始來源（先列清單再確認）

--to 只能指向已設定的來源；--all --to 不支援。

保護規則（逐項判斷，單項失敗不中止整批）

狀況行為
來源也被改了（兩邊都動）✘ 拒絕——覆蓋會清掉來源新內容，請人工合併
多 bucket 複本改成不同內容✘ 拒絕——由人決定哪份對（改成相同內容則視為一份，正常寫回）
來源檔已被刪除⚠ 明確詢問「要重建它嗎？」
來源根目錄不見✘ 拒絕——先修來源路徑
寫回目標在專案外（共用庫）⚠ 額外確認——影響所有用到該庫的專案

寫回後自動做的事

  • 改名過的 skill：自動把 SKILL.md 的 name 還原成原始名稱（-fromlib-… 只屬於產物，不能洩漏回來源）。
  • 多 bucket 複本同步為相同內容。
  • 更新 manifest 基準：status 不再對同一改動嘮叨，但會開始顯示 behind，提醒接著 apply。
  • --to 改道會提醒：舊來源的檔案還在，下次建置會收到新舊兩份同名——確認後手動刪舊的。

agsy clean

反安裝：確認後移除掛載連結與整個產物目錄，agsy.yaml 保留。只刪 agsy 建立的東西——真實目錄／檔案一律跳過並回報；manifest 記錄的孤兒連結會一併清（每條先驗證「確實是指向產物的連結」才動手）；連結刪除後變空的掛載目錄也一併移除。之後 agsy apply 可全部重建。

agsy version / agsy help

agsy version    # agsy v1.2.3 (commit …, built …, go 版本, 平台/架構)
agsy help       # 用法總覽（同 --help / -h）

C-3. 適配器（Adapters）

適配器是什麼？

內建的「各家工具掛載範本」：記錄工具的設定目錄、rules / skills / workflows 該連到哪個名字、以及專屬 bucket。只在 init 時發揮作用——你勾選工具，init 就把對應 mount 段落與 bucket 寫進 agsy.yaml；執行期 plan / apply / status 只看 agsy.yaml，所以 init 之後可任意手改，不受範本限制。

內建適配器一覽

Claude Code（bucket: claude，目錄 .claude/）

連結指向產物用途
.claude/rulesrules規則檔
.claude/skillsskillsAgent Skills
.claude/commandsworkflows/claude斜線指令——標 target: claude 的 workflow 在 Claude Code 中就是 /<檔名>

OpenAI Codex（bucket: codex，目錄 .codex/）

連結指向產物用途
.codex/promptsworkflows/codex自訂 prompts

只掛 workflows（遵循 Codex CLI custom prompts 慣例；原始碼註記專案層級支援仍待實測）。因此只勾 Codex 時 init 會警告：rules 和 skills 會建置但沒工具讀——需要可自行補 links。

Antigravity（bucket: agents，目錄 .agents/）

連結指向產物
.agents/rulesrules
.agents/skillsskills
.agents/workflowsworkflows/agents

bucket 與適配器的關係

每個適配器宣告一個 bucket。init 時 route.buckets＝勾選的適配器 bucket 聯集（＋手動加過的、＋自訂 mount 用到的）。workflow 以 target: 指名去哪些工具；沒標的依 route.default。

自訂掛載（接入不在清單的工具）

任何「從固定目錄讀 Markdown」的工具都能手動接上：

build:
  route:
    buckets: [claude, codex, mytool]   # 要有專屬 bucket 記得加
    default: [claude, codex, mytool]

mount:
  - dir: .mytool
    links:
      rules:   rules                # 共用 rules
      prompts: workflows/mytool     # 專屬 workflow bucket

規則回顧：目標第一層是某類別的 to；只有 workflows 可加第二層 bucket（須在 buckets 裡）；dir 不可重複、不可在產物或來源目錄內。自訂項目不會被 init 洗掉——之後再跑 init 編輯，自訂 mount 與 bucket 都原樣保留。

（進階）為 agsy 專案新增內建適配器

給想貢獻上游的人：內建適配器是 repo 內 adapters/ 下的 YAML，經 go:embed 打包。新增工具只要放一個 <name>.yaml：

# adapters/mytool.yaml
name: mytool          # 內部識別名
display: My Tool      # init 選單顯示名
bucket: mytool        # 專屬 workflow bucket
mount:
  dir: .mytool
  links:
    rules:   rules
    prompts: workflows/mytool

重新編譯後，init 的工具多選清單就會出現它。

D. Q&A 常見問題

觀念與日常使用

Q1：我直接改了 .claude/rules/ 裡的檔案，下次 apply 會不會被蓋掉？

.claude/rules 是指向 .agsy/rules 的連結，你改的是產物。apply 重建前會偵測到「本機改動」，先列清單問你要不要捨棄，不會不吭聲蓋掉。想保留：先 agsy promote 寫回來源，再 apply。

Q2：.agsy/ 要不要進版控？agsy.yaml 呢？

.agsy/ 不要（可重建產物，init 會主動幫你加 .gitignore）；agsy.yaml 要（專案同步設定，也是 init 編輯模式取代註解時的後悔藥）。

Q3：改了來源檔，工具什麼時候看到新內容？

跑完 agsy apply 之後。agsy 不是常駐程式、不自動監看——可配 git hook（agsy status exit 非 0 就提醒）。

Q4：plan、status、doctor 差在哪？

doctor＝環境健檢；plan＝這次建置的完整預演；status＝現況與基準的落差。三個都唯讀，隨便跑都安全。

Q5：可以在子目錄執行嗎？

可以，除 init 外都會往上層找 agsy.yaml。init 刻意只看目前目錄，避免誤改上層專案的設定。

Q6：多個專案共用一個來源庫？

可以，正是設計初衷。各專案的 sources 指向同一個 ~/all-ai-lib 即可。對共用庫 promote 寫回時會多一道確認（影響所有用到它的專案）。

「我的檔案怎麼了」

Q7：為什麼我的 skill 沒被收進去？

skill 必須是目錄＋內含 SKILL.md；目錄內不能有符號連結；名稱不能 . 開頭。doctor / plan 會直接告訴你原因。

Q8：rules 目錄裡某檔案沒被收？

rules / workflows 只收單一 .md：目錄、非 .md、. 開頭、符號連結都不收；原因列在 plan 的排除清單。

Q9：status 說有 untracked，apply 還會刪掉它？

untracked＝掛載側新增、manifest 不認識的檔案，沒有來源位置所以 promote 寫不回、apply 會刪。要保留：搬進某個來源的對應子目錄，再 apply。

Q10：檔名多了 -fromlib-xxx？

同名衝突 rename 策略附加的來源標籤：兩份都保留、看檔名知道來自哪個來源。skill 改名時 front-matter 的 name 也同步改寫（promote 時自動還原）。

Q11：workflow 沒出現在任何工具裡？

三種可能（plan 都會標）：target 指到不存在的 bucket（路由錯誤，apply 拒絕）；沒標 target 且 route.default 為空（不放，有警告）；標的 bucket 沒有任何 mount 連結去讀。

Q12：不小心刪了 .agsy/ 裡的東西？

沒事，產物本來就可重建：agsy apply 一次全部回來。manifest 壞掉時 apply 會多問一次確認再重建。

衝突與寫回

Q13：兩個來源同名檔案會怎樣？

由該類別 on_conflict 決定：rename 兩份都留（附標籤）；error 停下列清單；first 只留優先權高的。init 必答題，無隱含預設。

Q14：為什麼 skills 建議 error？

skill 靠描述語意觸發，同名並存時工具選哪個難預測；rename 還需改寫 SKILL.md 的 name。同名 skill 通常該整併，建議人工處理。

Q15：「來源也改了」promote 拒絕寫回？

保護機制：直接覆蓋會清掉來源新內容。手動比對兩份、把要留的合併進來源，然後 apply 重建，基準重設後恢復正常。

Q16：想把項目從共用庫搬到專案庫？

agsy promote skills/code-review --to ./repo-ai-lib

promote 完會提醒：舊來源那份還在，下次建置會收到兩份同名——確認新位置沒問題後手動刪舊的。

Q17：--all 和逐一寫回的差別？

--all 先按來源分組列出全部（寫到共用庫的特別標警告），確認一次後逐項寫回；單項失敗不中止整批，最後列失敗清單。--all 不能配 --to。

平台與環境

Q18：Windows 需要管理員權限或開發人員模式嗎？

不需要。agsy 用 junction，一般帳號即可建立。唯一注意：junction 存絕對路徑，搬移專案後要重跑 agsy apply（macOS / Linux 用相對 symlink，不受影響）。

Q19：換電腦／共用庫還沒 clone，status 一堆警告？

status 會明確區分「來源路徑不見」（repo 沒 clone、外接碟沒掛、路徑打錯）和「來源檔被刪」。此時 apply 也會拒絕重建，避免把缺席來源的項目清掉。補齊路徑再操作即可。

Q20：可以在 CI / git hook 用嗎？

可以：status exit 0/1 當檢查；動作類指令加 --yes；沒有 --yes 時非互動確認一律取消，不會意外破壞。agsy init --yes <sources...> 可非互動初始化。

Q21：介面語言怎麼切？

export AGSY_LANG=zh-TW＝繁中；AGSY_LANG=en＝英文；沒設時看 LC_ALL / LANG。

Q22：如何完全移除 agsy？

各專案 agsy clean → 不需要的話刪 agsy.yaml → 刪執行檔（macOS/Linux：/usr/local/bin/agsy；Windows：%LOCALAPPDATA%\Programs\agsy 並清 PATH）。

Q23：「孤兒連結」是什麼？

以前 apply 建過、後來你從 mount 設定拿掉的連結；工具還在透過它讀舊內容。apply 只回報不刪；手動刪或 agsy clean 一併清。

Q24：掛載點已有真實的 .claude/skills 目錄？

agsy 絕不刪非它建立的真實檔案。把既有內容搬進某個來源（讓它被 agsy 管理），或自行備份後刪除，再 apply。

Q25：來源裡的符號連結會不會把外部檔案（如私鑰）帶出去？

不會。掃描時符號連結一律不收（含 skill 內部——含連結的 skill 整個略過），複製階段還有第二道防線直接拒絕。產物會被掛載給各工具讀，這是刻意的安全設計。
